# 086 の実装中に判明した 065 の潜在バグ(2026-07-28)

## 症状

`live/tests/integration` を**通しで回すと 73/96 で永久にハング**する
(`test_collect_prospective_idempotent_across_runs`)。
**個別ファイル 20 本はすべて緑**で、単独実行では再現しない。

## 確定した原因(`pg_stat_activity` の直接観測)

```
96 | active | Lock/advisory | SELECT pg_advisory_lock(hashtext($1))   ← 待機
97 | idle   | ClientRead    | COMMIT                                   ← ExclusiveLock 保持
96 は 97 にブロックされている
```

`live/orchestrate.py::collect_prospective`(**feature 065**)が `pg_advisory_lock` を使う。
これは**セッションスコープ**で COMMIT では解放されず、しかも **Session ではなく
コネクションに紐づく**。`generate_recommendations` は途中でコミットする
(`betting/recommend.py:163`)ので、その時点でセッションは接続をプールに返し、
**ロックを保持したままの接続が idle でプールに残る**。
次の呼び出しが別の接続を引くと、その idle 接続に永久にブロックされる。

**単独実行で再現しない理由**: プール内の接続が 1 本しかなく同じ接続が再利用されるため、
セッションロックは再入可能で詰まらない。
**086 の `test_concurrent_reservations_over_the_cap_skip_backlog` が 8 スレッドで
プールを膨らませた結果、初めて別接続が割り当たり顕在化した。**

## 採らなかった修正と、その理由

- **`pg_advisory_xact_lock` への変更**: 誤り。`generate_recommendations` の途中コミットで
  早期解放され、check-then-insert のガードが無意味になる
  (`betting/cli.py:346-348` の既存コメントが同じ理由を明記している)。
- **`session.execute(pg_advisory_unlock)` を `finally` に置く**: **無効だった**(実測)。
  途中コミット後の `session` は別の接続を引くので、アンロックはロックを持たない接続で走り
  何も解放しない。**指摘した問題を修正自身が踏んでいた。**

## 採った修正

ロックの取得と解放を**専用接続に固定**し、`finally` でその接続上でアンロックしてから閉じる。
セッションロックの意味論(途中コミットを跨いで保持)は維持したまま、プールへの漏出だけを断つ。
086 のクールダウンが「捕捉トランザクションとは別セッションで独立コミットする」のと同じ考え方。

**結果**: 420 秒でハングしていた `tests/integration` が **96 passed / 98.9 秒**で完走。

## これは 086 のバグではない

065 の出荷済みコードの潜在欠陥で、086 のテストが炙り出した。
ただし**テスト固有ではない** — 本番でも `collect_prospective` を複数レースに回せば
同じ条件(プールに複数接続)が揃うため、実運用で詰まりうる。
