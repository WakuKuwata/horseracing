# Phase 0 Research: 上位3着ベースの荒れ度読み出し

**Feature**: 084-top3-chaos-readout | **Date**: 2026-07-26

NEEDS CLARIFICATION は残っていない。以下は設計判断とその根拠(codex 2 回のレビューで
提起された論点を含む)。**採用しなかった codex 指摘はゼロ**。

---

## D1: 事象確率の整合性をどう保証するか

**Decision**: 表示する全数値を**単一の順序三つ組同時分布**から導出する。事象ごとに独立した
isotonic を当てない。

**Rationale**: codex 第 1 回 #3 が指摘したとおり、事象別に独立校正すると
P(S≥30) ≤ P(S≥20) のような**入れ子事象の不等式が破れうる**。結果を見てから clip する後付けは
憲法 III 違反。1 個の同時分布から周辺化すれば、入れ子事象の整合は**構成上自動**で成立し、
事後の辻褄合わせが不要になる。

**Alternatives considered**:
- 事象別 isotonic → 不整合が出るので却下
- 分割(partition)の同時校正 → 整合はするが実装が重く、同時分布経由で同じ結果が得られる
- 順序制約付き射影 → 事前登録すれば可能だが、同時分布で不要になるため却下

**注意(実測)**: S≥20 と「二桁人気が3着以内」は**入れ子ではない**(5+7+8=20 のように二桁人気
なしで S≥20 が成立し、実測 8% で不等式が破れる)。整合制約は**入れ子事象にのみ**課す。
これを「バグ」と誤認して不等式を強制してはならない。

## D2: 同時分布の正規化 — 大域リスケールをしてはならない

**Decision**: テンソル和で割る大域正規化を**しない**。Σ(順序三つ組) = 1 を**不変条件**とし、
許容誤差を超えたら readout を unavailable にする(fail-closed)。

**Rationale**: 正規化された q に対し、各段の条件付き分布はそれぞれ和 1 になるので、
順序三つ組の和は任意の λ で厳密に 1 になる**はず**。和が 1 からずれるのは列挙漏れ・分母の
誤り・部分フィールド・epsilon floor バグのいずれかであり、大域正規化はそれを黙って隠す
(codex 第 2 回 #1)。

**実測による裏付け**(本 spec 起草中に確認)。**重要**: 下表は検証用に書いた**スクラッチのテンソル実装**の数値であり、
**本実装が使う `probability/engine.py::joint_probabilities` の挙動ではない**(エンジンは `_normalize_clip` で
q を [eps,1−eps] にクリップ+再正規化するため λ≤5 で頑健 — 実装後に測り直して Σ=1 が 6e-11 精度で保たれることを確認)。
スクラッチ側が崩れたのは `D3 = S3 − w3_a − w3_b` の引き算の桁落ちで、これは**エンジンを再利用すべき理由**であって
エンジンの欠陥ではない:

| λ2 / λ3 | ランダム 2,000 フィールドでの最悪 \|Σ−1\| |
|---|---|
| 1.0 / 1.0 | 4.5e-13 |
| **0.8304 / 0.7111(運用値)** | **1.3e-13** |
| 0.5 / 0.5 | 1.7e-14 |
| 0.1 / 5.0 | **6.6e-01** |
| 2.5 / 3.0 | **1.0e+00**(和が 5e-05 まで崩壊) |

実 DB 2020+ の全レース・運用 λ では最悪 |Σ−1| = **1.3e-15**。
既存 `joint_probabilities` を使った実測でも n=8/14/16/18 すべてで Σtrifecta =
`1.000000000000000`。一方 λ>1 側では D3 = S3 − w3_a − w3_b の引き算で桁落ちして崩壊する。
049 の λ 探索範囲は [0.1, 5.0] で λ>1 を許すため、**この assert が実際のガードになる**。

**Alternatives considered**: 自前のベクトル化テンソル実装 → 既存エンジンと二重実装になり
ドリフト源。codex 第 2 回 #1 の助言どおり `probability/engine.py::joint_probabilities` を
再利用する(marginal 整合と Σ=1 を既に保証している)。

## D3: 導出コアをどのパッケージに置くか

**Decision**: `probability/chaos_distribution.py`(純関数)。λ fit と境界 fit は `eval/chaos_bands.py`。

**Rationale**: 依存方向が `probability → eval` の一方向なので、`joint_probabilities` を使う
コードは eval に置けない(eval は probability を import できない)。一方 λ fit は
`eval/stage_discount.py` の条件付き NLL + golden-section だけで完結し probability を必要と
しないため eval に置ける。049 が同じ理由で導出コアを eval に置いた前例と整合する
(あちらは probability→eval のため eval 側だった)。

**Alternatives considered**: すべて api/ に置く → api は read-only の薄い層であるべきで、
数値コアを持つと 066 の `dispersion_bands.py`(eval)/`dispersion.py`(api)の分離規律に反する。

## D4: 表示時点スナップショットの凍結をどう実現するか(スキーマ変更なしで)

**Decision**: `live/` の CLI が **append-only JSONL artifact** に凍結する。API は読むだけ。

**Rationale**: `race_horses.odds` / `popularity` は憲法 V により単一最新値(closing 寄り)で
履歴を持たず、`win_odds_as_of` は汎用 `updated_at`(065 で「オッズ捕捉時刻ではない」と確定)。
凍結契約なしには estimand(「その時点で n 番人気だった馬」)が成立しない(codex 第 1 回 #1)。
API は全 path GET で AST / import-graph 境界テストにより書き込み不能なので、捕捉は
API に置けない(codex 第 2 回 #6)。`live/` は既に serving + betting を束ねる
オーケストレーション層で、019 で確立した唯一の書き込み可能な結線点。

**憲法 V との整合**: 「オッズのスナップショット履歴を DB に保存しない」方針は維持する。
凍結は **DB 外の表示監査用 artifact** であって、オッズ履歴テーブルの再導入ではない。

**Alternatives considered**:
- 新テーブル → スキーマ変更・migration が必要。本 feature の価値に対して重い
- `feature_snapshots` の再利用 → リーク境界(II)と既存契約(VI)を汚す
- 凍結しない → estimand が成立せず、前向き検証も不能

## D5: closing で fit した λ・バンド境界を発走前 snapshot に適用してよいか

**Decision**: **transport candidate として凍結し、前向き検証を通るまで補正後の率は provisional**。
`raw_market_mass` は即時公開。バンド境界は「closing 履歴の cut point」と明示する。

**Rationale**: λ とバンド境界は 2020-2023 の closing 寄りオッズで fit されており、
発走前スナップショットの分布とは一致しない可能性がある(codex 第 2 回 #2)。
最も post-hoc でない初手は、**現在の凍結値を変えずに最初の前向きコホートで挑戦させる**こと。
transport が失敗したら、1 つ目の前向きコホートで fit し、**厳密に後の 2 つ目**で確認する。

**Alternatives considered**: 即座に確定値として出す → 検証されていない数値を確定的に見せる
ことになり、まさに今回直そうとしている「剥離」の再生産。

## D7: バンドの軸と頭数交絡 — **【D11 で supersede】主軸は E[S] ではなく `P(S≥20)`**

**Decision(rev1・D11 で上書き済み)**: 主軸は E[S] の凍結窓五分位による 5 段スコアバンド。
**→ rev2 では `P(S≥20)` の五分位に変更(D11)。以下の頭数交絡の議論は軸に関わらず有効。**
旧記述: 「荒れ確率の五分位」とは呼ばない。頭数別バンドは**副次表示のみ**。

**Rationale**: ユーザーの定義は絶対的な人気番号(「18番人気が3着」)なので、絶対 S が正直な
主測度(codex 第 2 回 #3)。頭数依存は**真の情報**であって除去すべきバイアスではない
(S≥20 率は 8 頭以下 0.000 / 16-18 頭 0.148)。ただしバンドの頭数平均が 9.8→16.1 と偏るため、
N と実行可能サポート [6, 3N−3] を常時開示して「頭数エコー」を隠さない。

**Alternatives considered**:
- 頭数中立版 u=(rank−1)/(N−1) の期待値 → 絶対識別力を壊し(S≥20 AUC 0.776 → 0.587)、
  交絡が反転する(8 頭以下の 68% が最上位バンドに落ちる)。**主軸としては却下**
- 頭数別バケット五分位(066 の deferred v2) → 「同頭数帯内の相対位置」という別の問いに
  答えるものなので、副次表示としてのみ許可

**構造的ゼロの正確な境界**(codex 第 2 回 #3 の訂正を採用。当初の私の記述は誤り):

| 事象 | 不可能な頭数 | 根拠 |
|---|---|---|
| S≥20 | **N≤7** | 8 頭の最大は 8+7+6 = 21 なので 8 頭では**可能** |
| S≥30 | **N≤10** | 11 頭の最大は 11+10+9 = 30 |
| 二桁人気が3着以内 | **N≤9** | 10 番人気の馬が存在しない |

これらは確率 0 ではなく **structural zero(該当馬なし)** として表示する。

## D8: 人気順位の正本

**Decision**: 凍結 snapshot の明示的 `popularity` を唯一の正本とする。丸めオッズによる暗黙の
再ランクや馬番タイブレークは**禁止**。**重複・欠損があれば unavailable**とする。
**rev2 の是正**: 「1..N の完全な順列」を要求してはならない — 取消馬が人気番号を消費するため、
実測で**取消のあるレースの 26.1%** が max(popularity) > N になる(憲法 IV の取消除外と両立させる)。

**Rationale**: DB の `popularity` は 99.997% 埋まっている一方、オッズ順位との一致は 96.8%
(平均差 0.035)。**3.2% の不一致は無視できない**(codex 第 2 回 #4)。ユーザーが画面で見る
人気番号は `popularity` なので、こちらを正本にするのが表示との整合上も正しい。
同時分布を S に集約するときも**同じランク**を使う。

**Alternatives considered**: オッズ順位を正本 → 同着オッズのタイブレークが恣意的になり、
ユーザーが見る番号とずれる。

## D9: モデル p を荒れ度に使うか

**Decision**: 使わない。066 の「q 由来・p は差分表示のみ」を維持する。

**Rationale**: 同一レース集合(2024+)で市場 q(AUC 0.779)> 幾何平均 √(pq)(0.766)>
モデル p(0.733)。両モデル(lgbm-042 / lgbm-058-acc)で同じ順序。
レース単位 LightGBM(23 特徴・11 年 walk-forward)も市場 1 数値に log loss 11/11 年負け。

**限界の明示**: この p 側比較は**永続化 run(非 OOF)**由来なので provisional。
codex 第 1 回が指摘した厳密な検証(074 型 recipe-faithful OOF・q で定義した事象集合上で
Σ_{i∈S_q} p_i を集約・prior-only fold で両腕を同一校正)は **deferred**。
「いかなる荒れモデルも存在しえない」ことを示したわけではなく、
「この 23 特徴のレース単位モデルは事象特化の市場スコアに勝てなかった」が正しい主張。

## D11: バンド軸を E[S] → P(S≥20) に変更 (rev2)

**Decision**: 主値は `P(S≥20)`、バンドはその凍結窓五分位。E[S] は副次表示。

**Rationale**: 期待値は右に歪んだ離散分布の裾を隠す — 「95% が S=10・5% が S=30」と
「50% ずつ S=10/12」はどちらも E[S]=11 だが P(S≥20) は 5% と 0% で全く違う。
実測でも P(S≥20) が全ラベルで E[S] を上回る(S≥20: 0.779 vs 0.776 / S≥30: 0.861 vs 0.839 /
二桁人気3着内: 0.746 vs 0.735)。バンドとして使った場合の性能は実質同等
(spread ×35.3 vs ×32.4)だが、**確率そのものが解釈可能**であり、ユーザーが選んだ
「新しい荒れ確率の五分位で band を貼り直す」という表現にも忠実。

**確率としての実力**(2024+): Brier 0.0765(基準率のみの定数は 0.0841)・
log loss 0.2652(定数 0.3086)= 相対 9% 改善。

## D12: 事象は順序三つ組の走査中に評価する (rev2)

**Decision**: `chaos_distribution(q, ranks, events, ...)` が同時分布を 1 回走査し、
S の PMF と全事象質量を**同時に**集約する。

**Rationale**: rev1 の `event_probabilities(dist, events)` は S の PMF しか受け取らないが、
`himo_are` と `total_collapse` は**着順に依存**する。`(1,9,10)` と `(10,1,9)` はどちらも S=20 だが
両事象の値が違う。S に落とした時点で復元不能。`EventDefinition.predicate` は
**実行可能な型付き述語**でなければならない(rev1 は監査用文字列だった)。

## D13: λ は総崩れを校正できない (rev2・実測)

**Decision**: `total_collapse` に `lambda_sensitive=false` を持たせ、**生の市場質量である旨を
表示**し、`calibration_status` の対象から外し、昇格判定にも使わない。

**Rationale**: 049 の stage discount は λ1=1 固定(win バイト不変が設計要件)なので
**1 着 marginal は q に固定**される。したがって P(1着が二桁人気) = Σ_{rank≥10} q は
λ に**まったく依存しない**。実測 |差| = **5.6e-17**(200 フィールド・運用 λ)。
「校正済み」と表示すれば嘘になる。

## D14: 構造的ゼロは `0.0` + フラグ (rev2)

**Decision**: `event_mass = 0.0` + `is_structural_zero=true` + 理由。`None` にしない。

**Rationale**: 不可能な事象は「確率が不明」ではなく「確率 0」。`None` にして評価から落とすと、
少頭数の**確定陰性が Brier / log score / reliability から消え**、estimand が
「実行可能フィールドに限った risk」にすり替わる。UI では「該当馬なし」と描画すればよく、
それは**表示の都合であって統計的欠測ではない**。

## D15: 前向き証跡を DB 化 (rev2・ユーザー決定)

**Decision**: migration 0012 で `chaos_snapshots` / `chaos_readouts` を追加。

**Rationale**: rev1 は `artifacts/*.jsonl` に置いていたが `artifacts/` は **git 非追跡**で、
ローカルディスクと共に消える。数か月〜年単位の前向き研究の基盤にならない。
さらに rev1 は **reader(`prospective-report`)はあるが writer が無い**という致命的な穴があった。

**副次的な効果**: 凍結行が DB にあることで **API は `live` を import せずに読める**。
rev1 の「snapshot reader を live に置く」案は API → live の禁止依存を要求していた。

**憲法 V との整合**: 「オッズ履歴を持たない」は運用オッズ表 `race_horses.odds` の規約。
`recommendations.market_odds_used` が既に判断時点の凍結オッズを永続化している前例に載る。

**Alternatives considered**: git にコミットする案(年 3,500 行程度で小さく、git 履歴自体が
改ざん検知になる)も検討したが、書き込みが日次運用の一部になるため commit 運用に載せるのは脆い。

## D17: 主張の範囲を限定する — λ 不変条件 (rev2)

**Decision**: 契約を「**運用 λ で Σ=1 成功・敵対 λ で `ChaosInvariantError`**」とする。
`(0,5]` 全域が使えるとは主張しない。artifact 発行時に数値安定性ゲートを通す。

**Rationale(実装後に訂正)**: 当初は「18 頭・λ=1.5・極端 q で既存エンジンが 5.06e-04 まで崩壊」と
書いたが、**それはスクラッチ実装の数値でエンジンの挙動ではなかった**。実装後の測定では
エンジンは λ=(0.1,5.0) までランダム 720 フィールドで Σ=1 を 6e-11 精度で保つ。
不変条件が発火するのは**ほぼ退化したフィールド**(1 頭が実質全質量・他がクリップ前 1e-300 級)のみで、
**しかも引き金は λ ではなく `_normalize_clip` の eps クリップ**だった(実装後に測定:
退化フィールドで運用 λ なら INV-C5(1着 marginal 乖離 1.6e-10)、**λ=1 の生 provenance でも
INV-C1**(Σ 乖離 1.6e-9)が発火。クリップが 1e-300 を eps=1e-9 に持ち上げ支配馬の q を
1.0 → 0.999999983 にずらす)。現実的な極端フィールド 200 件では 0 件。
それでも fail-closed ガードの価値は変わらない(列挙漏れ・分母誤り・将来のエンジン変更を捕まえる)
ので契約は維持し、**テストの期待を「現実的フィールドで成功・退化フィールドで例外(λ 非依存)」に
正確化**し、偽陽性ガードの回帰テストを追加した。

## D18: 公平な比較 — エントロピーに同じ情報を与える (rev2)

**Decision**: 診断出力に **N のみ**と **`g(H, N)`** のベースラインを常に併記し、
**頭数バケット内の AUC / proper score** を報告する。

**Rationale**: 「E[S] はラベルと同じ人気順位を使うから有利なだけでは」という指摘は正当。
実測で答えると: エントロピーに頭数を与えた (H, N) ロジスティックは **0.7585**
(+交互作用項で 0.7626)。つまり生の 0.660→0.776 の**差の大部分は頭数**である。
ただし頭数バケット内でも E[S] が全帯で勝つ(N 9-11 で 0.768 vs 0.710 等)ので上乗せは本物。
「頭数正規化版の marginal AUC が 0.587 だから却下」は**増分の検定になっていない strawman**
だったので撤回する。

## D19: 「少頭数は常に堅い」は構造的事実ではない (rev2)

**Decision**: 少頭数の説明は「可能範囲は 6〜21」「二桁人気の馬はいません」という
**平易な事実**と、「同頭数のレースの中では低め/高め」の副表示で行う。

**Rationale**: **一様な 8 頭立ての E[S] は 13.50**(現行境界なら band ④)。
実データで少頭数が band ① に集まるのは**市場が集中しているから**であって、
頭数の構造的帰結ではない。rev1 の書き方は因果を取り違えていた。
