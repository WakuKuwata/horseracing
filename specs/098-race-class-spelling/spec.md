# Feature Specification: race_class の表記統一と再学習つき採否判定

**Feature Branch**: `098-race-class-spelling`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "race_class の表記ゆれ(JRA-VAN 期 `1勝/2勝/3勝/ｵｰﾌﾟﾝ/OP(L)` と netkeiba 期 `１勝/２勝/３勝/オープン`)を正規化し、再学習つき paired 評価で採否を決める。"

## 背景(2026-08-22 実測・この spec が前提とする事実)

- `race_class` は**カテゴリ特徴として生の文字列がそのままモデルに入る**。供給元が JRA-VAN(〜2025-10-05)から netkeiba(2025-10-11〜)に切り替わった後、同じクラスが別の綴りで届く: `1勝`(5,936 レース・2019-06〜2025-10-05)と `１勝`(824 レース・2025-10-11〜)、`ｵｰﾌﾟﾝ` 2,365+`OP(L)` 425 と `オープン` 164。**2026 年は全レースの 51%** が切替後綴り(`１勝` 604・`２勝` 296・`３勝` 136・`オープン` 119)。
- 現行稼働モデル(`lgbm-094-cap900`・学習終端 2026-08-16)の語彙には**両綴りが別カテゴリとして共存**している(加えて 2009〜2021 年の `重賞` 12 行という曖昧カテゴリ)。切替後綴りは学習データが 10 か月分しかない。
- 兄弟特徴 `class_transition` は既に NFKC で綴りを吸収しており無事。リステッド(`OP(L)`)は切替後 `オープン` に潰れ、`grade` 列も NULL(164/164)なので現状の DB からは区別できない。
- **固定モデルでの replay 測定(`scripts/killtest_class_spelling.py`、再学習なし・切替後 1,559 レース/94 開催日・arm B=未コミット txn 内で切替後綴りを JRA-VAN 綴りに書換→特徴再構築→rollback)は「直すと悪化」: winner NLL B−A = +0.0293、95% CI [+0.0254, +0.0333]。** 解釈: モデルは切替後綴りを「供給元切替後レジームの旗」として学習している(切替後は nk: サロゲート馬 39%・馬主/生産者 0%・血統系統 0%・脚質定義の変更・通過順欠落が同時に起きていた)。したがってこれは重賞修正(4472796)型の「serving 入力を書き換えれば直る欠陥」ではなく、**学習データ衛生の問題**であり、是非は**正規化したデータで再学習したモデル**と**非正規化のまま再学習したモデル**の対照でしか測れない。
- 同日に馬主/生産者(nk: 馬 100%)・血統系統(2026 行 90%)・通過順(欠損 0%)を修復したため、上記「レジームの旗」の価値は測定時点から変わっている可能性がある(memory `feature-health-audit-2026-08-22`)。

**この feature の性格**: null-is-success 型。「綴りを揃えるべき」は衛生上は自明に見えるが、実測は固定モデルに対して悪化を示した。採否は事前登録した paired 評価に従い、REJECT / NO_DECISION も正当な結果として扱う。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 綴り統一の価値を再学習つきで測る (Priority: P1)

運用者として、「`race_class` の綴りを統一してから学習したモデル」が「綴りが分裂したまま学習したモデル」より、切替後のレースで予測が良くなるかを、事前登録したゲートで一度だけ判定したい。固定モデルの replay は「悪化」を示したが、それは再学習を伴わない測定なので採否の根拠にならない。

**Why this priority**: 採否の根拠はこの測定だけ。正規化の結線と版 bump(US2)はこの測定が ADOPT を返すときに限って本番に入る。

**Independent Test**: 評価レポート 1 本で完結する。同一のデータ・同一の fold 分割・同一の学習レシピで、アーム A(綴り分裂のまま)とアーム B(綴り統一)を fold 内で再学習し、主測定(擬似分裂シミュレーション・FR-006)と実窓ガード(FR-006a)の winner NLL を paired で比較。両アームの差が「綴りだけ」であることを機械的に確認できる(採点レース集合・出走馬集合・他の全列が両アームで同一)。

**Acceptance Scenarios**:

1. **Given** 評価ゲート設定が実行前に凍結されている(hash 記録)、**When** US1 の評価を実行する、**Then** レポートは凍結 hash と一致し、verdict は ADOPT / REJECT / NO_DECISION のいずれか 1 つを機械的に返す(ボーダー数値の事後解釈で判定を変えない)。
2. **Given** アーム A とアーム B の特徴行列、**When** `race_class` 列を除いて比較する、**Then** 両アームはバイト同一であり、`race_class` 列の差異は規定の行(シミュレーションではカットオフ以降・実窓では切替後 2025-10-11 以降)にしか存在しない。
3. **Given** 評価が完走した、**When** 主測定(pool)の paired 差が δ=0.002 のゲートを満たさない、または実窓ガードが明確な悪化を示す、**Then** verdict は REJECT であり、本番データ・取込経路は一切変更されない。
4. **Given** verdict が ADOPT、**When** 後続の本番反映(US2)を行う、**Then** 反映は特徴層の正規化+版 bump と新版モデルの昇格だけで完了し、DB と取込経路は変更されない。

---

### User Story 2 - 綴りの正規化を特徴層で版に束ねて反映する (Priority: P2)

運用者として、ADOPT のときに、モデルが受け取る `race_class` が単一の正準綴りになるようにしたい。ただし DB の値(供給元の綴り)は書き換えず、正規化は**特徴の版**に束ねる: 新しい版で学習したモデルだけが正準綴りを読み、旧版で学習したモデルは従来どおり生の綴りを読む。これにより「正規化済みデータで学習したモデル」と「分裂したデータで学習したモデル」が同時に serve 可能になり、切替はモデルの昇格だけ、ロールバックもモデルの切戻しだけで済む(in-place の backfill が生むミスマッチ窓とロールバック不能を構造的に避ける=codex Q2)。

**Why this priority**: US1 が ADOPT を返したときだけ価値がある。US1 の測定でアーム B が使う変換はこの正規化そのものであり、測定と本番反映が同じ変換を共有する。

**Independent Test**: 同じ DB から旧版と新版の特徴を構築すると、`race_class` 以外の全列がバイト一致し、新版の `race_class` に切替後綴り(`１勝/２勝/３勝`)が残らない。ここで「特徴層」とは**特徴行列の構築後処理**(学習時のビルド・予測時の行)であり、features パッケージのビルド本体(静的列の算出・materialize)・DB・取込は不変である。旧版で学習した稼働モデルの予測は反映前後でバイト一致する。各 artifact が自分のカテゴリ語彙を hash で持ち、語彙が一致しない版の特徴で serve しようとすると拒否される。

**Acceptance Scenarios**:

1. **Given** 切替後綴りを含む DB、**When** 新版の特徴を構築する、**Then** `race_class` は `１勝→1勝`・`２勝→2勝`・`３勝→3勝` に揃い、表外の値(`オープン`・`重賞` 等)は不変で、件数が報告される。
2. **Given** 旧版で学習した稼働モデル、**When** 新版の正規化を結線した後に予測する、**Then** 予測は結線前とバイト一致する(旧版は生の綴りを読み続ける=値変更 bump の fail-closed/compat 規律に従う)。
3. **Given** 新版で学習した候補モデル、**When** 昇格する、**Then** serving は新版の特徴を読み、旧モデルへの切戻しは DB を触らずにモデルの切替だけで完了する。
4. **Given** 取込で未知の綴りが現れた、**When** 特徴を構築する、**Then** その値は変換されずに残り、監査に「変換表外の綴り」として件数と値が出る(黙って別カテゴリになることを検知できる)。

---

### User Story 3 - リステッド競走の復元可否を調べる (Priority: P3)

運用者として、切替後に `オープン` へ潰れたリステッド(`OP(L)`)を DB 内の情報、または既に取得済みのページから復元できるかを知りたい。復元に新規取得が必要なら、その範囲と件数を見積もって**本 feature の範囲外**として記録する。

**Why this priority**: 年 50 レース程度で規模は小さいが、`OP(L)` は 15 年分の学習カテゴリに存在し、切替後は構造的に出現しないので「綴り統一」だけでは埋まらない穴として記録しておく価値がある。

**Independent Test**: 調査メモ 1 本。切替後の `オープン` 164 レースのうちリステッドが何件あるかの推定、復元手段ごとの必要リクエスト数、結論(本 feature 内で可能/別 feature)。

**Acceptance Scenarios**:

1. **Given** 切替後の `オープン` レース、**When** 取得済みページ・DB の他列(賞金・レース名など)で判別を試みる、**Then** 判別できる件数・できない件数・必要な追加取得の有無が数字で記録される。

---

### Edge Cases

- 切替後綴りと JRA-VAN 綴りの**両方が存在しないクラス**(例: `重賞` 12 行・2009〜2021)は変換対象外として据え置き、件数を記録する。
- `オープン` は変換しない(FR-002)。将来 grade=`L` が読めるようになった場合は `OP(L)`、それ以外の `オープン` を `ｵｰﾌﾟﾝ` へ寄せる対応を別途事前登録する。grade が G1〜G3 の行は 4472796 の規則が優先される。
- 実窓ガードは検出力不足のため成立を要求しない。主測定(シミュレーション)が完走していれば verdict は原則 ADOPT/REJECT であり、NO_DECISION は「実行不能(充足未達=pooled 開催日数が凍結値未満を含む)」と「主測定+ガードが成立したのに transportability(FR-007a)が不成立」の 2 つだけ(FR-007 の優先順位)。
- 評価中に DB が動く(日次取込が走る)ため、測定ごと(主測定・実窓ガード)に両アームは**単一スナップショット(同一ビルド)のコピー**から構築し、アーム間で採点レース集合・出走馬集合が一致することを実行時に検査する(088 の教訓)。
- 固定の稼働モデルに正規化済みの入力を与えると replay 実測で +0.029 悪化する。したがって正規化は版に束ね、正規化を読むのは正規化で学習したモデルだけにする(FR-010)。DB を書き換えないので「修復の適用順序」という概念自体を持たない。
- DB の綴りは供給元のまま保存されるため、出馬表の再取得で値が「戻る」事故(重賞修復で起きた)は起きない。代わりに、供給元が綴りをさらに変えた場合は変換表外の値として監査に出る(US2 シナリオ 4)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 正準綴りは **JRA-VAN 綴り**(`1勝/2勝/3勝/ｵｰﾌﾟﾝ/OP(L)/Ｇ１/Ｇ２/Ｇ３/新馬/未勝利`)とし、対応は綴りの正規化キー(全角半角・かなの幅を畳んだ比較)で決める。理由: 15 年分の学習カテゴリと 4472796 の重賞修正に整合し、既存 artifact の語彙を壊さない。
- **FR-002**: 変換表は `１勝→1勝`、`２勝→2勝`、`３勝→3勝` に限定し、表に無い値は変換しない(推測しない)。**`オープン` は変換しない**: 切替後の `オープン` は JRA-VAN 期の `ｵｰﾌﾟﾝ`(リステッド以外)と `OP(L)`(リステッド)の**混合**であり、`ｵｰﾌﾟﾝ` に寄せることは綴りの統一ではなく意味の変更になる(codex Q3)。US3 でリステッドが独立に復元できた場合に限り `オープン→ｵｰﾌﾟﾝ / OP(L)` を別途事前登録して適用する。`重賞`(12 行)は特定の格の別名ではない粗い旧値なので据え置き。変換対象外の値と件数は特徴構築の監査で報告する。
- **FR-003**: US1 の測定は本番データを書き換えない。正規化は特徴構築時の変換(US2 と同一の変換表)としてアーム B にだけ適用し、DB・取込経路には一切触れない。
- **FR-004**: US1 は両アームを**同一 fold 内で再学習**する(保存済みモデルの流用禁止・学習レシピ/seed/列集合は同一)。アーム間の差は `race_class` の綴りのみであることを、`race_class` 列を除いた特徴行列のバイト一致と、採点レース集合・出走馬集合の一致で実行時に検査する。
- **FR-005**: 採否ゲートは評価契約 v4(paired winner NLL・開催日クラスタ bootstrap・再学習分散を含む区間・最小効果 δ=0.002)を**そのまま**使い、feature 固有の判定式を作らない。ゲート設定は実行前に凍結し hash を記録する。
- **FR-006**: **主測定=擬似分裂シミュレーション**(097 と同型・事前登録)。過去の事前登録カットオフ 3 本について「カットオフ以降のレースの `race_class` を切替後綴りに人工的に分裂させる」変換を施し、アーム A(分裂のまま)とアーム B(正準綴り)を**同一 fold 内で再学習**し、カットオフ+washout 1 年後の 1 年窓(互いに素)で paired 採点して pool する。カットオフ・washout・採点窓・δ・seed は実行前に凍結する。この測定が答えるのは「綴りの分裂そのものが再学習モデルにいくら損をさせるか」であり、実際の切替後に同時に起きた供給元レジームの差(nk: 馬・欠損・定義変更=「レジームの旗」)は**再現しない**ことを明記する。
- **FR-006a**: **実窓ガード**=切替後(2025-10-11 以降)の確定レースで同じ paired 評価を行い、方向一致(B が A より悪化しない・evidence-of-harm 幅は事前登録)をガードとする。検出力不足(MDE ≈ 0.009)のため成立は要求しないが、明確な悪化はゲートを落とす。実窓の結果は「レジームの旗」の交絡を含む反実仮想として報告し、過去予測の再構成とは読ませない。
- **FR-007**: verdict の正本は単一式 `primary_pooled(FR-006) AND guard_real_direction(FR-006a) AND transportable(FR-007a)` とし、個別カットオフ・部分窓の事後選別は禁止する(068 C2)。三値の優先順位は事前登録する: (1) 実行不能(完走不能・充足未達=pooled 開催日数が凍結値未満)→ NO_DECISION、(2) `primary_pooled AND guard_real_direction` が不成立 → REJECT(この場合 FR-007a は参考値として記録するのみで verdict を変えない)、(3) 両方成立したが `transportable` が不成立 → NO_DECISION、(4) 三つとも成立 → ADOPT。明確な REJECT を transportability の反転で NO_DECISION に変えることはしない。
- **FR-007a**: **transportability ゲート**(事前登録・codex Q4)。シミュレーションの平均効果が「データ品質レジームの異なる実データ」に移転できない危険に対し、(a) 各カットオフ単独の点推定の符号が pool と一致する、(b) leave-one-cutoff-out の pool(3 通り・点推定)が符号を保つ、(c) **実窓ガードの標本 CI が pool の符号を自信を持って否定しない**(pool が負なら実窓の `ci_low ≤ 0`。実窓の点推定そのものの符号一致は要求しない — 実窓の点推定は sd≈0.0045 で真の効果 −0.002 でも約 1/3 の確率で正になり、ノイズで NO_DECISION を量産するため)、を要求する。(a)(b) の符号反転または (c) の明確な否定が 1 つでもあれば verdict は NO_DECISION(平均で隠れた反転を ADOPT に変換しない)。これは事後選別ではなく、事前登録した一貫性条件である(research D6 と同一定義)。
- **FR-008**: REJECT / NO_DECISION の場合、FEATURE_VERSION・取込経路・DB は一切変更しない。正規化の変換表とその単体テストは非結線のまま保全し(062/070/090 同型)、負の結果(replay の +0.029 を含む)を記録する。
- **FR-009**: ADOPT の場合、正規化を**特徴層**に結線し FEATURE_VERSION を上げる(値変更 bump=017 前例)。ここで特徴層への結線とは、特徴行列の**構築後処理**として学習時のビルドと予測時の行に同一の純関数を適用することを指し、features パッケージの静的列算出・materialize(静的列は非 materialize)・DB の `race_class`・取込経路は変更しない(供給元の綴りを provenance として保持)。変換表は `１勝/２勝/３勝` の 3 対応に限定し(FR-002)、表外の値は不変・件数を監査に出す。
- **FR-010**: 正規化済みの `race_class` を読めるのは正規化で学習したモデルだけとする。旧版(分裂語彙)で学習した artifact は旧版の表現で serve を続け(compat 規律)、新旧の切替とロールバックはモデルの昇格/切戻しのみで完了する(DB のミスマッチ窓ゼロ・codex Q2)。
- **FR-011**: feature_hash は列名しか見ず綴りの違いを検知できないため、新版以降の各 artifact に**カテゴリ語彙(順序つき)の hash** と表現 marker を記録し、serving は特徴の版・表現・語彙 hash のすべてが一致しない限り拒否する。語彙 hash と marker を持たない旧版 artifact(features-021 以前)は、互換経路で生表現に限って serve を許す(旧版の語彙は生綴りで学習されている=FR-010)。新版以降で hash/marker が欠落した artifact は拒否する。旧版 artifact を再読込して予測がバイト一致することを反映前後で検証する(codex Q3)。
- **FR-012**: US3 の調査は読み取りのみで行い、netkeiba への新規取得は行わない。復元に取得が必要なら件数と見積もりを記録して範囲外とする。
- **FR-013**: リーク境界は不変(憲法 II): `race_class` は発走前に確定するレース属性であり、綴りの正規化は結果・オッズを一切読まない。as-of 集約・同日除外・自馬除外の挙動は変更しない。
- **FR-014**: 運用手順として、特徴構築の監査に「変換表外の `race_class` 値と件数」を常時出し、供給元が綴りを変えたときに黙って新カテゴリが生まれないようにする。結線後の最初の予測で、旧モデルの予測バイト一致と新モデルの語彙 hash 一致を 1 件ずつ確認する手順を quickstart に残す。

### Key Entities

- **race_class(レースのクラス表記)**: レース属性。カテゴリ特徴としてそのままモデル入力になる文字列。供給元ごとに綴りが異なる。
- **正準綴り表**: 切替後綴り→正準綴りの有限対応表(`１勝/２勝/３勝` のみ)。表外の値は不変。`オープン` は混合カテゴリとして据え置き(US3 の結果で別途事前登録)。
- **評価アーム**: A=綴り分裂のまま再学習、B=正準綴りで再学習。差は `race_class` の切替後行のみ。
- **ゲート設定(凍結)**: 評価契約 v4 の既定値と、シミュレーションのカットオフ 3 本・washout・採点窓・実窓ガードの幅・δ・seed・fold 定義。実行前に hash を記録。
- **語彙バインディング**: 各 artifact が持つ順序つきカテゴリ語彙の hash。特徴の版と合わせて serving の適合判定に使う(列名だけの feature_hash では綴りの差を検知できないため)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 評価レポート 1 本で verdict(ADOPT / REJECT / NO_DECISION)が機械的に 1 つ定まり、ゲート設定の hash が実行前の凍結値と一致する。主測定はカットオフ 3 本すべてで完走し、各カットオフの採点窓が互いに素である。
- **SC-002**: 両アームの特徴行列は `race_class` を除いて 100% バイト一致し、差異行はすべて(シミュレーションではカットオフ以降・実窓では 2025-10-11 以降の)対象レースに属する。
- **SC-003**: 同一 DB から旧版と新版の特徴を構築すると、`race_class` 以外の全列が 100% バイト一致し、新版の `race_class` に `１勝/２勝/３勝` が 0 行残る。DB の値は不変・新規 netkeiba リクエストは 0。
- **SC-004**: 旧版で学習した稼働モデルの予測は、正規化の結線前後でバイト一致する。語彙 hash が一致しない版の特徴で serve しようとすると 100% 拒否される。
- **SC-005**: ADOPT の場合、新版で学習したモデルの入力に切替後綴り(`１勝/２勝/３勝`)が残らず(`オープン` は据え置きとして件数を記録)、切戻しはモデルの切替だけで完了する(DB 操作ゼロ)。
- **SC-006**: REJECT / NO_DECISION の場合、FEATURE_VERSION・取込経路・DB が評価前と同一である。
- **SC-007**: US3 の調査メモに、切替後 `オープン` のうちリステッドと推定される件数、判別不能件数、必要な追加取得数が数字で記録される。

## Assumptions

- 正準綴りは JRA-VAN 綴りとする(FR-001)。全期間を NFKC 形へ寄せる案は、`Ｇ１`→`G1`・`ｵｰﾌﾟﾝ`→`オープン` と 2,365 行以上の歴史行まで書き換え、4472796 の判断を覆すため採らない。再学習する以上、綴りの選択はモデルには無差別であり、既存 artifact との互換だけが論点になる。
- 反映は**特徴層の正規化+FEATURE_VERSION bump**(値変更 bump=017 前例)で行い、DB は書き換えない(2026-08-23 ユーザー決定・codex Q2 採用)。理由: replay +0.029 は「モデルから見える意味変更」の証拠であり、データ修復(重賞・賞金)の前例とは性質が違う。in-place backfill はミスマッチ窓とロールバック不能を生む。列名のみの feature_hash では検知できないため語彙 hash を artifact に束ねる(FR-011)。
- 主測定は 097 型の擬似分裂シミュレーション(検出力を確保、pool で MDE ≈ 0.005=gate-config `power.mde_80` 0.0048)、実窓は方向ガード。切替後の実窓単独では検出力不足(MDE ≈ 0.009)なので主測定にしない(2026-08-23 ユーザー決定。codex は実窓主測定を推奨したが、その懸念=非交換性は FR-007a の transportability ゲートで受け、実窓の明確な悪化は REJECT とする)。`race_class` はレース内定数で race-softmax では主効果が相殺されるため、綴り分裂の実コストは交互作用経由の小さな量と見込む=null-is-success。
- 評価は単一 DB スナップショットから両アームを構築する(日次取込が並走するため)。
- 「レジームの旗」としての綴りが実際に情報を持つなら、それは綴りに載せるべきではない別情報(供給元レジーム)である。明示的なレジーム属性や 2×2 診断アームの導入は本 feature の範囲外とし、REJECT 時の follow-up 候補として記録する(codex Q1 の 2×2 案は不採用=計算 2 倍・採用しない指示子のため)。
- リステッドの復元は調査のみ。新規取得を伴う復元は別 feature。
- 本 feature の測定は `scripts/killtest_class_spelling.py`(固定モデル replay)を再現根拠として参照するが、採否には使わない(再学習を伴わないため)。
