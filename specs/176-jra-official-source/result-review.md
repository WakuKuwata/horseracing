## マージ前の確認(2026-11-02・netkeiba 経路が今まで通り取れるか)

利用者条件「今まで通り任意のタイミングで正しく取れるなら main にマージしてよい」に対して、稼働中の
fetcher が保存した実ページ(`artifacts/scrape_archive`・08/12〜11/01 の出馬表 5,894・結果 4,075)を
旧 main(`8e373520`)と新ブランチに同じ順で流し、最終状態を比べた(`scripts/netkeiba_replay/`)。
オッズは保存されていないので、各出馬表の取得時刻に確定オッズを揺らした値を合成した。入口は ops の更新と
同じ `scrape_entries` / `scrape_odds` / `scrape_results`、時計は各ページの取得時刻に固定。

| 流し方 | 東京 4 回(132 レース・2,129 件) | 全期間(3,713 レース・15,852 件) |
|---|---|---|
| 時系列順 | 全業務表が 1 行も違わない | 全業務表が 1 行も違わない(出走行 51,265・結果 10,152・単勝払戻 768・配当 7,664) |
| 全取得を 2 回+発走 1 時間後に出馬表・オッズ・結果をもう一度 | 全業務表が 1 行も違わない | 全業務表が 1 行も違わない |
| レースごとに順序を崩す(古いページが後から来る) | 差は取消 4 頭とその帰結だけ | 差 296 セルの全部が新コードの方が事実に近い(`judge_shuffle.py`・旧コードが正しい差は 0) |

全期間の崩した順序の差の内訳: 出走状態 16(取消を保つ)・騎手 13(古い出馬表で騎手変更を戻さない)・単勝と
人気 12・複勝 242+時刻 12(最新の発走前の値を採る/結果確定の後に届いた値は書かない=実運用では確定後の
netkeiba はオッズを返さないので起きない)・脚質 1(実際の出走頭数で導く)。

崩した順序の差はすべて、取消の後に古い出馬表が届いた場合だった。旧コードは取消馬を出走に戻し(176 で
直すと決めた既存欠陥)、新コードは取消を保つ。その帰結として、脚質を実際の出走頭数から導き、最新オッズを
「頭数不足」で捨てずに採り、取消馬に古いオッズを残さない。どれも実際に起きたことに近い側。

**再生で見つけた退行 1 件(修正済み)**: 共通 writer が netkeiba のサロゲート馬にも出馬表の性別を作成時に
書いていた(東京 4 回で 1,561 頭)。旧コードは書かず、プロフィールページから空欄だけ補完する=現在の性別。
出馬表の性別を最初に書くと、後に騸馬になった馬が「牡」のまま固まる。性別の初期値は公式経路の新規馬だけに直した。

**migration の順序**: 新コードを 0022 のままの DB で動かすと出馬表・オッズ・結果のジョブが全部失敗して 1 行も
入らない。0023 以上なら正常。旧コードを 0024 の DB で動かした結果は 0022 の DB と完全に同じ。したがって
**migration を先に当て、その後にコードを反映する**(ops の子プロセスは毎ジョブ稼働 checkout を読むので、
逆順だと反映した瞬間から取り込みが止まる)。API の `/health` は DB が同梱の最新版でないと 503 を返すので、
本番には 0023 と 0024 をまとめて当てる(0024 は空の表を 1 つ作るだけ)。

常設テスト `scrape/tests/integration/test_netkeiba_replay_regression.py`: 東京 4 レースの実ページ(取消 2 件を
含む・script/style を除去=除去前と最終状態が同じことを確認済み)と旧コードの最終状態を正解として固定し、
時系列順・二重取得は完全一致、崩した順序は差が真実の方向だけであることを毎回確かめる。

## 11/01 の実取得と FR-011a(2026-11-03・利用者決定「ID ルールを変える」)

**読むだけの実取得**(policy の複製で間隔 10 秒・業務表は不変): `jra-fetch --date 2026-11-01` で結果・払戻・出馬表・
変更情報・馬場の 18 件を 2 分 51 秒で取得、全件成功(保存先 `artifacts/jra_raw/2026-11-01/`)。

**見つかった阻害要因**: 2026 年の新馬は netkeiba 経路が `nk:X` で登録している。11/01 は 24 レース中 22 レース・
162 頭で、162 対すべて数字が公式コードと同じ、正規 `X` のマスタは 0 件(10/31 も 24 中 23 レース)。FR-009/011 の
ままだと公式経路の出馬表・オッズ・結果は約 92% のレースで隔離され、公式を先に書けば `nk:X` の履歴と割れる。

**FR-011a(spec に追記)**: 公式経路は出走行もマスタ行も作らず、同じレースの既存出走行(ID が `X` か `nk:X`)に
公式の値を書く。別名は 正規 `X` のマスタ無し・`id_mappings` 未判断・馬名一致 のときだけ。騎手・調教師は既存と
同じ人ならその ID、替わった人は netkeiba と確実に同じ ID になるときだけ。リンクなしの騎手・調教師はその項目を
残してレースは書く。レースの静的項目は既存値を書き換えず、空欄も数値(距離・賞金)しか埋めない。

**本番 DB の複製への再生**(`horseracing_replay176`・保存した 11/01 のページ・変更情報ページは翌開催分だったため除外):
初回で出馬表 24/24 レース(318 頭)・結果 24/24・払戻 48/48 を処理、`alias_horses` 162、隔離 0、
`race_static_kept` 32、`person_unlinked` 4(京都の 渡辺竜也 騎手 3 頭・笹野博司 調教師 1 頭)。
race_horses / race_results / races の値の変化 0、horses / jockeys / trainers / race_horses / id_mappings の行数の変化 0、
`race_laps` だけ欠けていた 23 レースを補完。2 回目の再生は全表不変。

**この再生で見つけた 2 件(修正済み)**:
1. 公式の出馬表がレースの静的項目を別表記で上書きしていた: `ダ`→`ダート`(9 レース)・`２勝`→`2勝クラス`(10)・
   `秋嶺S`→`秋嶺ステークス`(8)。芝ダとクラスは特徴量の入力。FR-011a 以前は公式経路がほぼ書けなかったので表に
   出ていなかった潜在欠陥。→ 既存値は書き換えない・文字の項目は空欄でも書かない。
2. リンクなしの騎手・調教師がいるとレースごと隔離していた(京都 3 レース)。→ その項目だけ残す。

**照合(jra-audit・本番 DB 読み取り専用)**: 別名の行を経由して比較するようにした結果、比較できた行が各項目
およそ 155 → 316 に増え、不一致は 走破タイム・上がり 3F 各 1(DB 側が空)と 結果ページの人気 8(保存しない項目)
だけ。払戻 7 券種 48/48・馬体重 259/259・騎手 313/313・調教師 315/315 一致。

**codex 実装レビュー**(MAJOR 3・MINOR 3): 人の解決で正規マスタがあると netkeiba の同一判定しだいで ID が変わる
→ 書かないに変更(採用)/ 正規マスタの作成や対応の承認はレースのロックを取らない → 067 修復 CLI を同時に流さない
運用の排他を manual に明記(採用・コード変更なし=通常運用で正規マスタを作る経路は無い)/ 空欄補完でも別表記が
入る → 文字の項目は書かない(採用)/ savepoint を分けても行ロックは外側トランザクション終了まで保持(問題なし)/
来歴: リンクなし・未解決の人は項目を書かないので来歴も付かない(確認済み)/ 追加テスト: 人の解決表・文字項目
を埋めない は追加、別接続の競合テストは上の運用排他で代える。
