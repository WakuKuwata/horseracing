**Feature Branch**: `176-jra-official-source`

**Created**: 2026-11-01

**Status**: Draft(clarify 済み・plan 済み 2026-11-01・tasks 済み 2026-11-02=[tasks.md](tasks.md)。plan 段階の codex レビューで FR-001/015/023・SC-004/009・US2 シナリオ 1/4・US3 シナリオ 1 の表現を是正=[research.md D21](research.md)。**US2 シナリオ 1/4 の「人気を書く→保存しない」は利用者が 2026-11-02 に承認**(別表は作らない))

**Input**: User description: "JRA 公式サイト(www.jra.go.jp/JRADB)を第 2 の情報源として追加する。netkeiba は置き換えず並走させる。POST cname で索引→開催日→レースを辿り、出馬表(開催日 1 ページ)・レース結果(開催日 1 ページ・馬体重/推定上り/通過順/ハロンタイム/人気/払戻)・単複オッズ(1 レース 1 ページ・更新時刻つき)・払戻金・変更情報(取消/発走時刻変更/騎手変更)・馬場情報(含水率・クッション値の HTML 断片)を取り込む。馬/騎手/調教師の ID は JRA 10 桁/5 桁コードで既存 DB の canonical ID と同一なので id_mappings を経由せず直接結合し nk: サロゲートを作らない。既存契約(race_horses/race_results/official_win_payouts/decision_quotes)への純追加で、スキーマは馬場情報(含水率・クッション値)だけ新テーブルを検討。調査記録は docs/research/jra-official-site-survey-20261101.md。"

## 背景と動機

2025 年半ばに JRA-VAN の年次 CSV が止まり、2026 年のレースは netkeiba が唯一の情報源になった。その結果、

- netkeiba 経由で入った馬・騎手・調教師の多くが正規 ID に結び付かず `nk:` サロゲート(2026-11-01 時点で馬 5,545 頭)として分裂し、過去走の履歴が切れた馬がデビュー扱いで予測されている(067 の問題)。
- 取得先が 1 社に集中しているため、取得予算(10 秒間隔・1 日 1 万件でブロックの実績)が運用上の上限になっている。
- 含水率・クッション値・変更速報(取消/発走時刻変更/騎手変更)のように netkeiba にない公式情報を使えていない。

2026-11-01 の調査([docs/research/jra-official-site-survey-20261101.md](../../docs/research/jra-official-site-survey-20261101.md))で、公式サイトはブラウザ自動化なしの単純な POST で読め、全ページがサーバ描画の HTML で、馬・騎手・調教師の ID が既存 DB の正規 ID と**そのまま一致**することが確認できた。本 feature はこの経路を netkeiba と並走する第 2 の情報源として製品に入れる。

**この feature が約束しないこと**: 予測精度や回収率の改善。取得先を増やしても鮮度は数分差で、173〜175 で確定した「判断時から締切までに売れて支払価格が下がる」壁はこの feature では動かない。価値は正規 ID・公式値・取得予算の分散・公式にしかない情報の 4 点にある。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 当日の出馬表・変更情報・単複オッズを公式から取り込む (Priority: P1)

運用者が開催日に 1 コマンドで公式サイトから出馬表(全レース・1 ページ)と変更情報(取消・発走時刻変更・騎手変更)を取り込み、必要なレースの単勝・複勝オッズを「HH 時 MM 分現在」の時刻つきで取り込む。取り込まれた馬・騎手・調教師は既存の正規 ID に直接結び付き、新しい `nk:` 行は 1 つも増えない。

**Why this priority**: 製品の表示・予測・判断記録はすべて出走表とオッズから始まる。正規 ID で結び付くことが 067 の分裂を止める唯一の経路でもある。

**Independent Test**: 2026-11-01 東京の保存 HTML(出馬表・変更情報・11R 単複オッズ)を入力に、netkeiba 経由で同日に保存された行と比較する。出走馬の馬番・馬名・騎手・調教師・斤量が全頭一致し、取消馬が取消として記録され、オッズ行に公式ページの時刻が来歴として残ること。

**Acceptance Scenarios**:

1. **Given** 開催日の索引ページだけが分かっている状態, **When** 運用者が当日の出馬表取込を実行する, **Then** その日の全レース・全出走馬が既存の出走表契約に書かれ、馬・騎手・調教師の ID は公式コードがそのまま正規 ID として使われる。
2. **Given** 変更情報に「5 番 出走取消」がある, **When** 出馬表と変更情報を取り込む, **Then** 当該馬は出走取消として記録され、出馬表側で馬番が「取消」に置き換わっていても馬番 5 が失われない。
3. **Given** 既存 DB に同じ正規 ID の馬が別名で登録されている, **When** 取り込む, **Then** その馬のマスタ行は上書きされず、不一致として件数と ID が報告に出る。
4. **Given** 単複オッズページに「8 時 30 分現在オッズ」とある, **When** オッズを取り込む, **Then** 公式の表示時刻は `official_at`(値の公式時刻)に、取得した時計の時刻は `observed_at`(観測時刻)に、別々に残る(140 の来歴契約と同じ意味で)。
5. **Given** 同じレースのオッズを 2 回続けて取り込み、公式ページの表示時刻が進んでいない, **When** 2 回目を実行する, **Then** オッズの値と `official_at` は変わらない(業務値の冪等)。`observed_at` と取込ジョブの記録だけが進む。
6. **Given** 同じレース・同じ馬番の出走行が既に `nk:` サロゲートの馬で保存されている, **When** 公式の出馬表(正規 ID)を取り込む, **Then** その行は書き換えられず、レース単位で隔離され「同一馬候補」として ID の対が報告に出る(二重出走行を作らない)。

### User Story 2 - レース結果と払戻金を公式から取り込む (Priority: P1)

運用者が開催日の夜に 1 コマンドで公式のレース結果(着順・タイム・着差・コーナー通過順・推定上り・馬体重(増減)・単勝人気・ハロンタイム・天候・馬場)と全券種の払戻金を取り込む。公式単勝払戻は既存の精算契約(139)に、同着は複数行で入る。

**Why this priority**: 138/139/174/175 の精算は公式単勝払戻で行う。公式サイトから直接取れれば精算の正本が文字どおり公式になる。結果の馬体重と人気は netkeiba 由来の値の裏取りにもなる。

**Independent Test**: 2026-10-31 東京の保存 HTML(結果・払戻)を入力に、既に netkeiba 経由で保存された同日の結果行・払戻行と比較する。着順・タイム・馬体重・払戻額が一致し、同着レースは複数行になること。

**Acceptance Scenarios**:

1. **Given** 結果が未保存のレース, **When** 公式の結果を取り込む, **Then** 着順・タイム・着差・通過順・上り・ハロンタイムが結果契約に、馬体重(増減)が出走表契約に書かれ、払戻は単勝が精算契約に、他の 6 券種が配当契約に書かれる。単勝人気は保存せず監査の比較材料にだけ使う(plan D9: 公式に確定オッズの数値が無く、人気だけを書くと発走前オッズと確定人気の不整合行になる。**利用者決定 2026-11-02**)。
2. **Given** 結果が既に netkeiba 経由で保存されているレース, **When** 公式の結果を取り込む, **Then** 既存の結果行は上書きも NULL 補完もされず(INSERT-ONLY の規律)、値の不一致は件数と内容が報告に出る。先に届いた方が残る規律であり「公式が正」とは呼ばない。
3. **Given** 1 着同着のレース, **When** 払戻を取り込む, **Then** 単勝払戻が勝ち馬ごとに 1 行ずつ入り、精算が同着を区別できる。
4. **Given** 公式の結果ページに単勝オッズの数値が無い, **When** 取り込む, **Then** 確定オッズは捏造されず、既存のオッズも人気も消されない。公式の人気順位は保存せず、保存済みの人気との不一致を報告に出す(plan D9・利用者決定 2026-11-02)。

### User Story 3 - 二重情報源の整合を監査する (Priority: P2)

運用者が任意の日付範囲について、netkeiba 由来と公式由来の値がどれだけ一致しているか(出走馬集合・馬番・斤量・馬体重・着順・払戻)と、公式経由で正規 ID に結び付いた馬のうち既存 `nk:` 行と同一個体と思われる数を、読み取り専用で確認できる。

**Why this priority**: 2 つの情報源を並走させる以上、「どちらが正しいか」を測る計器なしに精度や精算の議論はできない。`nk:` の統合(067)に進むかどうかもこの数で決まる。

**Independent Test**: 同じ開催日の両経路の保存行を突き合わせ、フィールドごとの一致率と不一致の内訳を出す。DB に書き込まない。

**Acceptance Scenarios**:

1. **Given** 収集工程(`jra-fetch`)で保存した公式ページと、同じ開催日の保存行, **When** 照合工程(`jra-audit`)を実行する, **Then** フィールドごとに比較可能件数・一致率・不一致件数・不一致例が別々に表示され(来歴不明・未解決 ID・公開段階違いは比較可能件数から分けて数える)、照合工程は DB を変更しない。単一最新値の規律(憲法 V)の下では「両経路の保存値を並べる」ことはできないので、比較は「公式の解析値 vs 保存値」で行う(plan D13)。
2. **Given** 公式経路で正規 ID の馬が入り、同名・同生年の `nk:` 行が既にある, **When** 監査を実行する, **Then** 「統合候補」として件数と ID の対が表示されるが、統合は行われない。

### User Story 4 - 馬場情報(含水率・クッション値)を保存する (Priority: P3)

運用者が開催日ごとに公式の馬場情報(競馬場・測定時刻・芝/ダート × ゴール前/4 コーナーの含水率・芝のクッション値・馬場状態・天候)を保存できる。保存した値は表示・研究用で、予測の特徴量には本 feature では使わない。

**Why this priority**: netkeiba に無い唯一の新情報だが、特徴化にはリーク境界(利用可能タイミング=朝 5:30〜7:00 の測定)と別の採否ゲートが要るので、保存までを本 feature の範囲とする。

**Independent Test**: 保存 HTML 断片を入力に、測定時刻ごとの行が重複なく保存され、再実行で増えないこと。特徴量ビルドが新テーブルを読まないことがテストで固定されていること。

**Acceptance Scenarios**:

1. **Given** 公式の含水率・クッション値断片, **When** 取り込む, **Then** (競馬場, 測定時刻) ごとに 1 行が保存され、同じ断片を再度取り込んでも行は増えない。
2. **Given** 新テーブルが存在する状態, **When** 特徴量を構築する, **Then** 新テーブルの値はどの特徴にも現れない(リーク境界テスト)。

### Edge Cases

- 開催日ページの一部のレースだけが未発表・中止・順延のとき: レースごとに「未発表 / 確定 / 中止 / 解析失敗」を区別し、発表済みレースだけを取り込む。欠落を削除や取消に変換しない。ジョブは PARTIAL として件数つきで記録する。
- 開催日ページの見出し(年・回・日次・場・R)と期待する `race_id` が食い違う: 日付から `race_id` を推測せず、見出しと照合できたレースだけを書く。
- 出馬表で取消馬の馬番セルが「取消」に置き換わる: 行の順番から馬番を推定してはならない。変更情報ページの「N 番 馬名」と、既存出走行の公式 ID との一致から解決する。解決できなければそのレースを隔離し、取消馬を黙って除いた出馬表を「完全」と判定しない。
- 取消を含むレースに、取消前に保存された古い出馬表を再投入する: 取消状態は戻らない(状態遷移は一方向)。空の馬体重で既存の馬体重を消さない。
- 公式ページの構造が変わった(列見出し・class 名・行数が想定と違う): 黙って空や部分値を書かず、そのレースは無書込みにし「構造不一致」として報告する(fail-closed)。HTTP 200 で返るエラー画面も同様。
- アクセス拒否(403/429)と、パラメータ不整合(error013・パラメータエラー)は分ける: 前者は共有 cooldown、後者は原因つきで停止し索引からの辿り直しを回数制限つきで許す。両方を一律に長い cooldown にすると実装不具合を隠す。
- 同じ公式コードが既存マスタと別名のとき(改名・表記ゆれ): マスタを上書きせず異常として報告する。名前照合は異常検知であって、同一性の証明や結合キーではない。
- 「前日最終オッズ」ページと当日オッズページの区別: 前日最終は `official_at` が前日になる。当日の値を前日値で巻き戻さない(140 の逆行拒否)。確定オッズとして投入もしない。
- 公式オッズと netkeiba オッズが交互に書かれる: `official_at` が比較可能な場合は新しい方が残り、同時刻で値が異なる場合は固定の優先順位(公式)で決めて競合を記録する。`official_at` が不明な値を取得時刻だけで「新しい」と判定しない。
- 払戻の同着・返還(取消馬の単勝 100 円返還)・不成立券種: 同着は勝ち馬ごとに行を作り、返還と不成立は行を作らず件数を報告する。訂正で勝ち馬集合が変わった場合は券種ごとの集合として置き換え、旧行を残さない。
- 公式の結果ページに確定単勝オッズの数値が無い: 人気や払戻額からオッズを捏造しない。既存の精算経路(確定オッズ+払戻の同時処理)に対して、払戻だけを接続できること。
- 取得制限の共有: 索引・開催日・レース・馬場断片を含む**すべて**の要求が共有スロットを通り、ホストごとに独立した間隔を持つ。174 の捕捉時間帯に入ったら次のホップから取得を止める。
- 2026 年の過去日が索引から辿れない: 到達できない日は unsupported として明示し、エラーにしない。

## Requirements *(mandatory)*

### Functional Requirements

**取得経路**

- **FR-001**: 公式サイトの取得は、固定の索引から開催日ページ、レースページへとリンクを辿る方式でなければならない。リンクのパラメータ(cname)を自前で生成・改変してはならない。cname は運用で再利用する遷移情報として永続化せず、起動ごとに索引から取り直す(テスト fixture と取得 archive は raw HTML を証跡として保持してよいが、そこから cname を読んで再利用してはならない。manifest には cname のハッシュだけを書く)。
- **FR-002**: 取得はブラウザ自動化を使わず、通常の HTTP 要求で行い、Shift_JIS を正しく復号しなければならない。
- **FR-003**: 公式サイトへの**すべて**の要求(索引・開催日・レース・馬場断片・JSON)は既存の共有スロット機構(093/172)を通らなければならない。公式サイトのホストは netkeiba と別のスロット鍵を持ち、間隔は設定ファイル(`source-operations.json`)の専用キーで与える。下限は netkeiba の下限と同じ値以上とし、呼び出し側が短縮できてはならない。間隔が設定経路から届かない場合は 1 件も送らない(現行実装は netkeiba 以外の間隔が 0 秒なので、この経路を塞ぐことが受入条件)。
- **FR-004**: 174 の捕捉時間帯(`capture_only_dates` の日の窓)に入ったら、捕捉プロセス以外の公式取得は次のホップから止めなければならない。
- **FR-005**: 拒否(HTTP 403/429・Retry-After)と、パラメータ不整合(error013・パラメータエラー・HTTP 200 のエラー画面)を区別しなければならない。拒否は再試行せず当日の取込を止め共有 cooldown に記録する。不整合は原因つきで停止し、索引からの辿り直しを回数制限つきで許す。
- **FR-006**: すべての取込は `ingestion_jobs` に専用の job_type(`jra_entries`・`jra_odds`・`jra_results`・`jra_payouts`・`jra_changes`・`jra_baba`)と**経路を示す source**で記録し、処理件数・skip 件数・隔離件数・不一致件数・PARTIAL 判定・エラーを summary に残す。既存のジョブ記録が source を netkeiba 固定で書く箇所は、そのまま再利用してはならない。
- **FR-007**: 解析器は保存 HTML(fixture)だけでテストでき、ネットワークを使ってはならない。fixture は取得時刻・文字コード・ハッシュとともにリポジトリに保存する。調査で保存した 2026-10-31/11-01 のページを初期集合とする。
- **FR-008**: 解析器は想定外の構造(列見出し・必須セルの欠落・レース数や見出しの不整合・文字化け・別日のページ)を検出したら、そのレースを無書込みにして失敗を記録しなければならない(fail-closed)。開催日ページは 12 レース揃った完全な写しとは扱わず、レースごとに「未発表 / 確定 / 中止 / 解析失敗」を判定する。

**識別子**

- **FR-009**: 公式サイトの馬(血統登録番号 10 桁)・騎手(5 桁)・調教師(5 桁)コードは、JRA が発行する正規 ID と同一の名前空間として、`id_mappings` を経由せずそのまま正規 ID に使う。エンティティごとの契約(桁数・先頭ゼロの保持・リンクの形式・未知 ID の扱い)を spec の Key Entities に固定する。本 feature の経路から `nk:` サロゲートを作ってはならない。
- **FR-010**: 既存マスタに同じ ID がある場合、正規化(NFKC・空白除去)した名前が一致しなければ、マスタ行を変更せず異常として ID と両名を報告しなければならない。一致してもマスタは触らない。名前照合は異常検知であって、同一性の証明や結合キーに使ってはならない。ID が無い場合だけ新規行を作る(馬は data_source=`jra_official`)。
- **FR-011**: 同じレースの出走行が既に `nk:` サロゲート(または別 ID)で保存されていて、公式ページが同じ馬番に正規 ID を示す場合、馬番の一致だけで ID を書き換えてはならない。既存出走行の ID との一致、または承認済みの `id_mappings` を必須とし、満たさないレースは隔離して「同一馬候補」(名前・生年が一致する対)として報告する。既存の `nk:` 行の統合は 067 の再キー手順に委ね、本 feature では行わない。

**書き込みと優先順位**

- **FR-012**: 出馬表(枠・馬番・馬名・性齢・斤量・騎手・調教師・馬体重と増減・単勝オッズ・発走時刻・距離/コース)は既存の出走表契約(`race_horses`・`races`)に書く。取消は `entry_status` に、発走時刻変更は `races.post_time` に反映する。
- **FR-013**: 単勝・複勝オッズは既存の `update_odds` 契約に従い、結果未確定レースのみ書く。公式ページの表示時刻は `official_at`(値の公式時刻)に、取得時刻は `observed_at` に、140 と同じ意味で分けて残す。日付・JST・「前日最終 / 当日現在」の種別を解決し、分精度の限界を保持する。`official_at` が保存済みより古い場合は値も来歴も書かない。レース単位の来歴更新は全馬のオッズと同一トランザクションで行い、一部だけ更新して全体を最新扱いにしない。
- **FR-014**: レース結果は既存の INSERT-ONLY 規律に従い、結果行が無いレースだけ書く。既に結果がある場合は上書きも NULL 補完もせず、値の不一致を件数と内容で報告する(既存の列単位の補完例外は列挙されたものに限る)。初回到着順で残る値が決まるので、これを「公式が正」と呼ばない。
- **FR-015**: 公式単勝払戻は `official_win_payouts` に勝ち馬ごとの行として書く。他の券種の払戻は既存の確定配当契約(`exotic_odds`、quote と dividend の分離規律)への写像(組番・金額単位・返還・発売なしの扱い)を固定したうえで書く。対象は製品の 7 券種(単勝・複勝・馬連・馬単・ワイド・3連複・3連単)で、**枠連は対象外**(憲法と `BetType` の定義どおり。公式ページの枠連は件数だけ報告する)。払戻は券種ごとの**集合**として、券種ブロックの状態(未発表 / 完全 / 発売なし / 返還のみ / 解析失敗)を判定したうえで、完全な券種だけ検証・置換し、訂正で勝ち馬集合が変わった場合に旧行を残さない。未発表と発売なしを区別し、空の券種で既存行を消さない。同額の公式払戻でも採用元は公式に移る。HTML ハッシュだけで集合の正しさを主張しない。
- **FR-016**: 両経路が同じレースに値を持つ場合の規則は、公式経路だけでなく既存の netkeiba 書込み経路にも**共通に**適用し、判定と更新は DB 内で原子的に行う。項目別の規則: (a) 結果=先に届いた行を保持、訂正は別フロー。(b) 払戻=確定済みの完全な公式ブロックを優先し、以後 netkeiba で戻さない。(c) 取消・騎手変更・発走時刻・馬体重=項目別の状態遷移を定義し、古い出馬表で取消を解除せず、空の馬体重で既存値を消さない。(d) オッズ=比較可能な `official_at` の新しい方が残り逆行は拒否、同時刻の異値は固定優先順位(公式)で決め競合を記録する。(e) 出走表の静的項目(枠・馬番・斤量・騎手・調教師)=不一致を報告し、公式を正とする。**利用者決定(2026-11-01): この項目別規則で確定**(codex 推奨 A)。
- **FR-017**: 書き込まれた値がどの経路・どの時刻・どのジョブ由来かを後から判別できなければならない。`race_horses` は出馬表・馬体重・取消・オッズが別々の時刻に別々の経路から更新されるので、可変項目群ごとに source・時刻・ジョブ参照を持てる形を plan で決める。結果行のように一度だけ挿入される行は行単位で足りる。既存の由来不明の行を netkeiba 由来と決めつけない。
- **FR-018**: 174 の判断記録 `decision_quotes` は本 feature で変更しない。T−3 の quote は netkeiba 経路のままとし、公式経路の quote を混ぜない(年内の比較は単一経路で続ける)。
- **FR-019**: 公式の結果ページには確定単勝オッズの数値が無い。人気や払戻額からオッズを捏造せず、既存のオッズを消さず、既存の精算経路に払戻だけを接続できるようにする。前日最終オッズを当日現在値や確定オッズとして投入してはならない。

**馬場情報**

- **FR-020**: 含水率(芝/ダート × ゴール前/4 コーナー)・クッション値・馬場状態・天候を、(競馬場, 測定時刻, 項目) を一意とする新テーブルに保存する。測定時刻 `measured_at`、取得時刻 `fetched_at`、確認できる場合の公表時刻 `published_at`(不明なら null)を分けて持つ。後刻取得した値を「その時刻に公表済み」とみなさない。再取込で行は増えず、後日訂正・遅延公表・過去履歴の後日取得・未来日付をテストする。
- **FR-021**: 新テーブルは本 feature では特徴量・予測・買い目に使わない。特徴量構築が新テーブルを読まないことをテストで固定する。特徴化は利用可能タイミングを定義した別 spec で審査する。

**運用**

- **FR-022**: 取込は CLI の手動実行とする(`--date` 指定・`--dry-run` あり)。v1 は当日と索引から到達できる日に限り、辿れない日は unsupported として明示する。ops の更新ボタンや worker への結線は範囲外。
- **FR-023**: 監査(US3)は収集工程と照合工程に分ける。収集工程(`jra-fetch`)は公式ページを取得して raw を保存するだけで業務表・ジョブ記録に書かない(共有スロットの予約行だけは動く)。照合工程(`jra-audit`)は保存した raw を入力に、DB を読み取り専用トランザクションで開き、「公式の解析値」と「保存値」を「同じレース・同じ公開段階(結果前 / 結果後)・解決済み ID」の行同士で比較する。比較可能件数と一致率を分けて出し、来歴不明・未解決 ID・公開段階違い・時刻差・公式に存在しない確定オッズは比較対象外として別々に数える。保存値の由来は来歴があればそれを添え、無ければ「不明」と表示する(netkeiba と決めつけない)。

**範囲外(明示)**

- **FR-024**: 2026 年の過去開催の一括 backfill と、`nk:` 行の正規 ID への置換(再キー)は本 feature の範囲外とし、別 spec(067 系の ID 移行: 外部キー・過去走集約・materialize・保存済み判断との参照整合・移行前後 parity・ロールバック)で扱う。本 feature の通常取込で起きる `nk:` 衝突は FR-011 で隔離する。**利用者決定(2026-11-01): 別 spec に分ける**(codex 推奨 A)。176 は当日と索引から到達できる日に限る。
- **FR-025**: 馬ページ(過去走一覧)・券種別オッズグリッド・票数(公式サイトにも無い)・レース動画・騎手/調教師ページは範囲外。

### Key Entities *(include if feature involves data)*

- **公式ページ参照(cname)**: 索引から辿って得た遷移パラメータ。保存せず、起動ごとに索引から取り直す。チェック値を含むため生成不可。キャッシュする場合は URL でなく cname を鍵にする(別レースの応答を混同しない)。
- **公式 ID の名前空間契約**: 馬=血統登録番号 10 桁(リンク `pw01dud00` の直後 10 桁・先頭ゼロ保持・文字列)、騎手=5 桁(`pw04kmk0` の直後・先頭ゼロ保持・例 `05339`)、調教師=5 桁(`pw05cmk0` の直後・例 `01165`)。桁数・数字以外・リンク形式不一致は未知 ID として隔離。騎手と調教師の同じ数値は別エンティティ。
- **出走表行(既存 `race_horses`)**: 公式コードが正規 ID。馬体重・増減・斤量・単勝オッズ・取消状態。
- **レース(既存 `races`)**: 発走時刻・距離・コース・天候・馬場状態。変更情報による発走時刻更新。
- **結果行(既存 `race_results`)**: 着順・タイム・着差・コーナー通過順・推定上り 3F。INSERT-ONLY。
- **公式単勝払戻(既存 `official_win_payouts`)**: 勝ち馬ごとの払戻額。同着は複数行。
- **確定配当(既存 `exotic_odds`)**: 券種ごとの組番と払戻。
- **馬場情報(新規)**: 競馬場・測定時刻・含水率 4 値・クッション値・馬場状態(芝/ダート)・天候・取得元ページの指紋。
- **取込ジョブ(既存 `ingestion_jobs`)**: 経路を示す job_type と件数・不一致・エラーの summary。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 2026-11-01 東京の出馬表を公式から取り込んだ結果が、同日 netkeiba 経由の保存行と、出走馬集合・馬番・騎手・調教師・斤量で 100% 一致する(取消馬は状態の一致まで)。
- **SC-002**: 公式経路の取込で新しく作られる `nk:` 行は 0 件。公式経路で入った馬・騎手・調教師 ID のうち既存マスタと名前が一致しないものは全件が報告に出る。
- **SC-003**: 2026-10-31 東京の結果・払戻を公式から取り込んだ結果が、netkeiba 由来の保存行と着順・タイム・馬体重・単勝払戻額で 100% 一致し、同着レースは勝ち馬の数だけ払戻行がある。
- **SC-004**: 単複オッズの `official_at` は公式ページの表示時刻と一致し、同じ表示時刻での再取込は値と `official_at` が変化 0(`observed_at` と取込ジョブの参照だけが進む=FR-013)。
- **SC-005**: 開催 2 場・各 12 レースの 1 日あたり公式要求数は、出馬表+変更情報+結果+払戻+馬場で 20 件以下、単複オッズを全レース 1 回取っても 50 件以下。
- **SC-006**: 公式サイトへの要求間隔は設定値以上であることがテストで確認され、間隔未設定では 1 件も送られない。
- **SC-007**: 構造が変わった fixture(列の欠落・見出しの変更)に対して解析器は部分値を書かずに失敗する。
- **SC-008**: 馬場情報テーブルを特徴量構築が参照しないことをテストで固定し、既存の予測(active モデル)の出力はこの feature の前後でバイト一致する。
- **SC-009**: 本 feature が既存 API 応答・front・admin・ops の OpenAPI を変更しない(drift-check 緑)。DB の変更は plan が列挙するものに限る: `source` 系 CHECK の値追加(`jra_official` / `jra_official_result`)、来歴 2 表(`race_field_provenance` / `race_horse_field_provenance`)、馬場表(`jra_track_conditions`)。既存表の列は追加も変更もしない。
- **SC-010**: 二重投入の契約テスト(netkeiba→公式→netkeiba、公式→netkeiba→公式、同一データ再投入、古い時刻、同時刻異値、途中失敗後の再実行、並行実行)で、業務値が規則どおりに不変・JRA-VAN 由来行が無変更・二重出走行 0・競合が記録される。
- **SC-011**: `nk:` の馬が既に出走行を持つレースに公式出馬表を投入しても、既存行は 1 行も変わらず、隔離レース数と同一馬候補の対が報告に出る。
- **SC-012**: 通信テストで、索引・POST・リダイレクト・馬場断片を含む全要求が共有スロットを通り、別プロセスと競合しても間隔が守られ、DB 障害時は 1 件も送られず、捕捉時間帯に入ると次のホップで止まる。

## Assumptions

- 公式サイトの利用条件(2026-11-01 時点の「ご利用に際して」)に自動取得の禁止条項はなく、robots.txt は全許可。間隔を守った少量の読み取りは許容されると判断する。条項が変わればこの feature の取得は止める。
- 公式コードと既存 DB の正規 ID は同一名前空間(JRA 発行の血統登録番号・騎手コード・調教師コード)である。調査で馬 1 頭・騎手 2 名・調教師 3 名を実値で確認した。憲法 I の「id_mappings なしの横断利用禁止」は異なる発行元(netkeiba)の ID についての規律であり、同一発行元の ID の直接利用はこれに反しないと解釈する。安全弁として名前照合(FR-010)を置く。
- 公式サイトのオッズ更新は数分間隔で、`Cache-Control: max-age=20`。取込は手動で、自動スケジューラは置かない(憲法の初期方針)。
- 票数(売上額)は公式サイトにも無い。プール規模が必要なら JRA-VAN Data Lab の別 feature。
- 2026-11-01 時点の HTML 構造(class 名 `h_weight`・`odds_tan`・`refund_unit` 等)を fixture の正とする。構造変更は fail-closed で検知する。
- 開催日には運用中の netkeiba 経路(174 の捕捉・ops の更新)が動いている。本 feature の CLI は同じ共有スロットと捕捉時間帯の規律を守るので、並走しても取得間隔の契約は破れない。
- 既存の upsert 契約(`upsert_entries`・`update_odds`・`apply_final_odds`・`upsert_official_win_payouts`・`upsert_exotic_odds`)を再利用し、新しい書き込みロジックは経路の違い(ID 解決と優先順位)だけに限る。
