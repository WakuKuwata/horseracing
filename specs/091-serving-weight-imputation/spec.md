# Feature Specification: 馬体重欠損時の serving 入力是正 (Serving Weight Imputation)

**Feature Branch**: `091-serving-weight-imputation`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: "馬体重欠損時の serving 入力是正(前走体重の特徴化)。ライブ予測時は馬体重が 97.4% 欠損するのに学習時は 0.3% しか欠損しない train/serve スキューを、前走体重・体重の鮮度・体重有無を独立列として与えることで是正する。"

## 背景と問題

馬体重 `weight` と増減 `weight_diff` は、欠損時に補完せず NaN のままモデルに渡している([static_features.py:37](../../features/src/horseracing_features/static_features.py) の "no impute")。これは Unknown と 0 を区別する憲法 IV に忠実な設計であり、それ自体は正しい。

しかし実 DB を測ると、**この欠損は学習時とライブ予測時で発生率が桁違い**である:

| コホート | 行数 | `weight` NULL | 欠損率 |
|---|---|---|---|
| 結果未確定(=これから予測する行) | 508 | 495 | **97.4%** |
| 全履歴の `race_horses`(取消含む) | 961,098 | 2,427 | 0.3% |
| **学習母集団(started かつ結果確定)** | **956,099** | **1** | **0.0001%** |

**実装時に判明した訂正(2026-08-10)**: 当初は学習側の欠損率を 0.3% と書いていたが、それは取消行を含む `race_horses` 全体の数字だった。**実際に学習に使われる母集団(started かつ結果確定)では欠損は 956,099 行中わずか 1 行**である(しかもその 1 行はデビュー戦なので前走体重も無い)。started 行の欠損 452 行のうち **451 行は未確定レース側**にある。つまりスキューは当初の記述よりさらに極端で、**学習中にモデルは「体重なし」という入力をただの一度も見ない**。これが「mask は付随的な工夫ではなく機構の本体」である理由を、数字の上でも裏づけている(配線 smoke で実測: mask 前 0 行 → mask 後 429,399 行)。

原因は構造的である。netkeiba の出馬表は馬体重を発走約 50 分前まで「計不」として出さず、一方で予測実行の中央値は発走 6.7 時間前([086 の実測](../086-capture-on-predict/spec.md))。つまり**利用者が予測を見る時点では、ほぼ常に馬体重が存在しない**。

勾配ブースティング木の欠損分岐は「学習中に観測した欠損パターン」から方向を学ぶ。学習データに欠損がほぼ存在しない以上、serving 時の NaN ルーティングは実質的に未学習であり、恣意的な方向に流れている。

**これはモデルの問題でも学習の問題でもなく、train/serve スキューである。** 精度レバーが枯れたとする総括([accuracy-levers-exhausted])は「新しい特徴の追加」についての結論であり、既存入力が serving 時に壊れている問題はその射程外にある。

### 実測(kill-test、2026-08-09)

active モデル `lgbm-064-f02acc` を**固定**し(再学習なし)、serving 入力だけを差し替えて反実仮想 replay を行った。母集団は 2021-01-01..2026-07-12 の確定済 19,113 レース(単一勝者のレースのみ)。指標はレース単位 winner NLL、CI は開催日クラスタ bootstrap 95%(全アームで同一 draw を共有)。

| arm | 内容 | winner NLL |
|---|---|---|
| A | 実体重 + 実 `weight_diff` | 2.047232 |
| B | 両方 NaN(**現行のライブ挙動**) | 2.065976 |
| C | 前走体重 + `weight_diff`=NaN | 2.053700 |
| D | 実体重 + `weight_diff`=NaN(oracle 参照) | 2.049703 |

- **C−B = −0.012275**、CI [−0.014649, −0.009987]、有意。この repo で歴代最大級だった target encoding や 085 arm E と同じ桁の改善である。
- B−D = +0.016273(体重本体を失う代償)、D−A = +0.002470(`weight_diff` の寄与。**当日体重なしには原理的に再現不能**)
- C−D = +0.003998。全馬に前走体重がある層に限れば +0.001 まで縮む = 前走体重は実体重のほぼ代替として機能する。

頑健性(すべて同一 kill-test 内で確認):

- **校正前**(race-softmax 直後)でも C−B = −0.011269。isotonic が arm A 分布で fit されている副作用ではない。
- **2021〜2026 の全 6 年で有意**(−0.0106〜−0.0142)。最大は 2026 年。
- 体重の鮮度(`weight_age_days` = 今走日 − 前走体重の実測日)で層別しても **>365 日で −0.0105 と有意** → 休養明けを除外する上限は不要。
- 前走体重の母集団を「出走馬のみ」に限るか「取消を含む直近観測値」にするかは C−C2 = −0.000018(ns)= **無関係**。
- 前走体重が 1 頭も無い層では C−B が厳密に +0.000000(実装健全性の確認になっている)。
- 高速評価経路は serving の `predict_race` と全アーム × 5 コホートでパリティ PASS(race-softmax 段は完全一致、最終正規化のみ 1 ULP)。

適用可能性: 現在の未確定レースでは、体重欠損 451 行のうち 405 行(**89.8%**)に前走体重が存在する。

体重データ品質: 実測範囲 330–640 kg、非正値ゼロ、範囲外ゼロ、同一馬同日の重複エントリゼロ。外れ値ガードは不要。

証跡(スクリプトと JSON レポート)は [`evidence/`](./evidence/) に収めた。



### この実測が証明していないこと(正直な限界)

- **arm D は oracle 参照であって数学的な回収上限ではない。** 固定した非線形モデルの下では、前走体重が実体重を上回ることも原理的にありうる。「回収可能上限」とは呼ばない。
- **arm B は 100% 欠損のストレス版**である(実運用は 97.4%)。本番なら残る 2.6% には当日体重を使う。
- **主測定窓は production replay であって将来性能の OOS 証拠ではない。** booster の学習は 2020-08-30 で止まっており測定窓は booster に対して OOS だが、isotonic 校正器の fit 窓(2020-08-30..2026-07-12)の内側である。完全 OOS の 2026-07-13 以降は 252 レースしかなく、CI が広く NO_DECISION になる公算が高いため測定していない。校正前アームの一致がより強い反証になっている。
- kill-test は「既存 `weight` 列に前走体重を流し込む」形の測定である。本 feature が採る**独立列方式は未測定**であり、採否は本 feature の事前登録ゲートで改めて判定する。

### 設計の核(codex レビューを採用)

**前走体重を `weight` 列に混ぜない。** 学習時=当日体重・serving 時=前走体重を同じ列に入れると、モデルは両者を区別できずスキューが残る。代わりに前走体重を**独立列**として与え、モデル自身に「これは N 日前の代理値である」ことを踏まえた重み付けをさせる。独立列方式は kill-test で測った混入方式を包含する(木は体重の有無で分岐して同じ関数を構成できる)うえ、鮮度に応じた割引を追加で学習できる。

**ただし新規列は 1 本だけでよい。** モデルが必要とする 3 つの情報のうち、**鮮度と有無は既存列がすでに完全に供給している**ことが実測で判明した(plan 段階・262,733 行):

| 必要な情報 | 供給元 | 状態 |
|---|---|---|
| 代理値そのもの | **新規列 `prev_weight`** | 追加する |
| 代理値の鮮度 | 既存の「前走からの経過日数」 | **100% 一致**(差 0 行・欠損パターンも同一) |
| 代理値の有無 | 既存の「過去走の有無」 | **100% 一致** |

前走体重の供給元を「出走かつ体重あり」に限ると、出走行の 99.95% に体重があるため「直近の計量済み出走」が事実上つねに「前走」と一致する。したがって専用の鮮度列・有無列を作っても既存列の複製にしかならない。冗長列は木の容量を食い寄与の帰属も曖昧にするため追加しない(research D1)。

**学習側の欠損付与はレース単位で行う。** 欠損は行単位でランダムに発生するのではなく、時間帯 regime 単位(そのレースの予測がいつ実行されたか)で発生する。行単位のランダム mask は現実の欠損構造と異なり、モデルに「同じレース内に体重が分かる馬と分からない馬が混在する」という**起きないと想定している**状況を学習させてしまう。

> **レース内混在は設計で解消する。** 混在が実際に起きるかは未検証である(結果未確定レースは揮発的で母集団が取れず、体重の履歴スナップショットも保存していないため遡及確認もできない)。目的関数がレース内 softmax である以上、混在が起きればレース単位 mask で学習したモデルにとって out-of-distribution になり、本 feature が是正しようとしているのと同型のスキューを小規模に再導入してしまう。
>
> そこで**測って対処するのではなく、起きない形にする**: serving 側で体重の可用性を**レース単位に正規化**し、started 馬に一頭でも未計量がいればそのレースは全馬 serving regime として扱う(FR-034)。学習は全馬 masked か全馬 full-info の二値なので、serving も同じ二値に倒せば本番の入力分布が学習分布と厳密に一致する。失うのは「混在レースで一部の馬に当日体重がある」という情報だけで、混在は計量公表中の短い遷移窓でしか起きないはずである(research D12)。

**採用ゲートは serving regime で測る。** ここが本 feature で最も間違えやすい点である。標準の paired-eval は体重が存在する確定済レースで評価するため、その条件下では新列に価値がなく、feature は無価値に見える。実際に予測が行われる条件(体重欠損)で測らなければ、測りたい効果を測れない。

### 本評価の結果(2026-08-12・T048)

候補 `lgbm-091-wmask`(features-021 + race-atomic mask m=0.5/seed 20260810)vs 現行相当(`prev_weight` を持たないアーム)を、凍結した gate-config(hash `c3594766…`)のもと **2021-01-01..2026-08-09 の 19,430 レース**で paired 評価した。

| 判定項目 | 結果 |
|---|---|
| **PRIMARY: serving regime** | **−0.010592** CI[−0.012841, −0.008215](n=19,400) |
| effect > δ=0.002 / CI 上限 < 0 | PASS / PASS |
| top2 非劣化 / top3 非劣化 | PASS / PASS |
| ECE 非劣化 / 緊急停止 | PASS / PASS |
| **GUARD: full-info regime** | +0.000369 CI[−0.001141, +0.001977] → **PASS**(幅 0.003 以内) |
| **GUARD: subgroup**(2026_only / nk / 2026_nk) | **PASS / PASS / PASS** |
| **verdict.status** | **ADOPT** |

**校正前(race-softmax 直後)でも −0.010393** CI[−0.012317, −0.008356]。方向も大きさもほぼ同一なので、**isotonic の副産物ではない**(codex が必須とした診断)。

**kill-test との照合**: 固定モデルの replay は C−B = −0.0123 を示していた。独立列 + mask の再学習で **−0.0106**、予測の 86% を再現した。plan 段階で「独立列方式そのものは未測定」と限界を明示していた部分が埋まったことになる。

**当初の懸念は外れた**: 学習ログの full-info(per-horse LogLoss +0.0045)から「mask の代償が非劣化幅を超えるかもしれない」と警告していたが、paired・レース単位で測ると **+0.0004** に留まった。指標の異なるものを比べて心配していた。

**再現性の限界(正直な記録)**: 本評価は 3 回実行し、serving diff は −0.010507 / −0.010507 / −0.010592 とばらついた(幅 8.5e-5)。原因は LightGBM のスレッド別勾配集約で、**凍結設定が宣言していた `num_threads: 1` を CLI に渡していなかった**ため。効果量の 0.81%・CI 半幅の 3.7% であり結論には影響しないが、「決定論的に測った」という記録は事実と違っていた。以後は gate-config の宣言を CLI が自動で適用し、実際に使った値を snapshot に記録する。3 回とも同じ verdict・同じ subgroup 判定だったことは、結論の安定性の傍証として残す。

### 診断アーム m=0.0 — mask が機構の本体であることの対照実験

| arm | serving regime 差 | 95% CI |
|---|---|---|
| m=0.5(採用構成) | −0.010592 | [−0.012841, −0.008215] |
| **m=0.0(列はあるが mask なし)** | **+0.000278** | [−0.001221, +0.001802] |

**`prev_weight` 列を足すだけでは効果はゼロと区別できない。** plan で「mask は付随的な工夫ではなく
機構の本体」と論証した点(mask が無ければ木は当日体重で分割し、前走体重を採用しないので serving では
元の未学習 NaN 分岐に戻る)が、対照実験で実証された。この 2 アームは `artifact_kind="diagnostic"` /
`eligible_for_verdict=false` で刻まれ、verdict loader が構造的に弾く(事後採用の禁止、068 C2)。

| レース | started / 計量済 | 正規化 | `logic_version` の marker |

未確定レースで serving regime を確認することは**現時点ではできない**(未確定 1 レースが全頭計量済み)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 発走前の予測が体重欠損で劣化しない (Priority: P1)

予測を見る利用者として、発走の数時間前(馬体重がまだ公表されていない時点)にレース詳細を開いたとき、その予測が「体重という情報が丸ごと抜け落ちた状態」ではなく、その馬の直近の体重とその鮮度を織り込んだ状態で計算されていてほしい。

**Why this priority**: これが feature の存在理由そのもの。利用者が実際に予測を見るのは 97.4% の確率でこの条件下であり、現状そこで winner NLL が 0.0187 悪化している。

**Independent Test**: 体重が未公表のレース(結果未確定・`weight` が NULL)に対して予測を生成し、そのモデル入力に前走体重・鮮度・有無が渡っていること、および同一レースを体重ありで再計算したときとの差が現行より小さいことを確認する。

**Acceptance Scenarios**:

1. **Given** 過去に出走歴のある馬が出走する体重未公表のレース、**When** 予測を生成する、**Then** その馬のモデル入力に直近出走時の体重・その実測日からの経過日数・体重ありフラグが渡っている
2. **Given** デビュー馬(前走なし)、**When** 予測を生成する、**Then** 前走体重は欠損のまま渡され、0 や集団平均で埋められていない。体重ありフラグは「なし」を示す
3. **Given** 前走が取消で体重が記録されていない馬、**When** 予測を生成する、**Then** さらに前の「出走かつ体重あり」の走の体重が使われる(体重の無い走を単に一つ前として採用しない)
4. **Given** 同一レースの出馬表、**When** 前走体重を解決する、**Then** 対象レースと同日以前に開催された同日レースの体重は使われない(同日除外)
5. **Given** 体重が公表済みのレース、**When** 予測を生成する、**Then** 当日体重と増減はこれまでどおり使われ、前走体重列はそれと併存する(当日体重が上書きされない)
6. **Given** 出走 16 頭のうち 3 頭だけ体重が公表されたレースで、前走体重を入力に持つモデルを使う、**When** 予測を生成する、**Then** 公表済みの 3 頭も含めて**全馬**の当日体重が使われず、全馬が前走体重で予測される(レース内で混在した入力がモデルに渡らない)
7. **Given** 同じ混在レースで、**前走体重を入力に持たない現行モデル**を使う、**When** 予測を生成する、**Then** 可用性正規化は発動せず、公表済み 3 頭の当日体重はこれまでどおり使われる(代替値を持たないモデルから情報を取り上げない)
8. **Given** 出走馬は全頭計量済みだが取消馬に未計量の馬がいるレース、**When** 予測を生成する、**Then** 正規化は発動しない(判定は出走馬のみを見る)

### User Story 2 - 採否を serving 条件で判定する (Priority: P2)

運用者として、この変更を本番モデルに入れるかどうかを、「実際に予測が行われる条件」での測定結果に基づいて、事前に決めた基準で機械的に判定したい。数値を見てから基準を動かすことはしない。

**Why this priority**: US1 の構築だけでは採否が決まらない。またこの feature は評価条件を間違えると効果がゼロに見えるため、評価設計自体が成果物である。

**Independent Test**: 候補モデルと現行 active モデルを同一レース集合・同一 fold で paired 再評価し、serving regime と full-info regime の双方でレポートが出ること、verdict が事前登録した式から一意に決まることを確認する。

**Acceptance Scenarios**:

1. **Given** 候補モデルと active モデル、**When** serving regime(体重 3 列をレース単位でマスク)で paired 評価する、**Then** レース単位 winner NLL の差と開催日クラスタ bootstrap CI が出力される
2. **Given** 同じ 2 モデル、**When** full-info regime(体重あり)で評価する、**Then** 非劣化ガードの判定結果が出力される
3. **Given** 評価レポート、**When** verdict を読む、**Then** 採否は単一の事前登録済みフィールドから決まり、個別数値の事後解釈による読み替えが行われない
4. **Given** 評価が実行不能(データ不足等)、**When** verdict を読む、**Then** ADOPT でも REJECT でもなく NO_DECISION が返る
5. **Given** ゲート設定、**When** 本評価を開始する、**Then** 設定は評価前に凍結され、以後の変更は検知されて評価が失敗する

### User Story 3 - 特徴の利用可能タイミング宣言を実態に合わせる (Priority: P3)

将来この repo を触る人として、「その特徴がいつ使えるようになるか」の宣言が実態と一致していてほしい。宣言が嘘だと、時点別に入力を制御する仕組みを作ったときに、静かなリークか静かな欠損を生む。

**Why this priority**: 現時点の予測値には影響しない(宣言を読んで分岐する実装がまだ無い)。ただし本 feature はまさに「いつ何が使えるか」を扱うので、同じ変更セットで直すのが自然である。

**Independent Test**: レジストリの宣言と実装の依存関係を突き合わせ、宣言より遅い入力に依存する列が存在しないことを機械的に確認する。

**Acceptance Scenarios**:

1. **Given** 斤量を馬体重で割った比率の列、**When** その利用可能タイミング宣言を読む、**Then** 「馬体重後」になっている(現状は「出馬表前」だが実装は馬体重に依存している)
2. **Given** 宣言修正の前後、**When** 特徴量行列を生成する、**Then** 全列の値と列名の一覧は完全に一致する(宣言はメタデータであり値を変えない)
3. **Given** レジストリ全体、**When** 各列の宣言と実際の入力依存を突き合わせる、**Then** 宣言より遅い入力に依存する列が他に存在しないことが確認される

---

### Edge Cases

- **前走体重が存在しない馬**(真のデビュー馬、または個体分裂で履歴が繋がっていない馬): 欠損のまま渡す。0 埋め・集団平均補完はしない。kill-test ではこの層で C=B が厳密一致した。なお履歴が繋がらない原因が個体分裂([067](../067-entity-identity-resolution/spec.md) の `nk:` サロゲート)である馬を、真のデビュー馬と同一視して報告しない。
- **極端に古い前走体重**(最大 2,143 日 = 約 6 年): 除外しない。kill-test で >365 日でも有意な改善があった。鮮度は既存の「前走からの経過日数」がそのまま表すので、割引の判断はモデルに委ねる。ただし鮮度帯ごとのカバレッジと効果は監査に出す。
- **前走が取消・除外**: 「出走かつ体重あり」の走まで遡る。取消時にも計量されている場合があるが、それを使うかどうかは kill-test で無差(−0.000018, ns)だったため、出走のみを正とする。
- **同一馬が同日に複数レースに登録**: 実 DB では 0 件。発生した場合は前走体重を欠損とする(安定ソート任せで暗黙に一方を選ばない)。
- **体重の異常値**: 実 DB では範囲 330–640 kg で逸脱ゼロ。それでも非正値・明らかな範囲外は前走体重の供給元として採用しない。
- **体重が公表済みのレース**: 当日体重が優先され、前走体重列はそれと併存する。当日体重が前走体重で上書きされることは決してない。
- **レース内で体重の有無が混在**(計量公表中の遷移窓に予測が走る): 前走体重を持つモデルなら**全馬を体重なし扱いに倒す**(FR-034)。公表済みの馬の当日体重は捨てる。混在した入力を渡すと、レース内 softmax を通じて 1 頭の入力変化が全馬の確率を動かし、race-atomic mask で学習したモデルにとって out-of-distribution になるため。前走体重を持たないモデルには適用しない(FR-034a)。
- **取消馬だけが未計量**: 正規化は発動しない。判定は started 馬に対してのみ行う。
- **確定済レースの体重欠損**(全履歴の 0.3%): backfill も同じ正規化を通る(FR-034b)。「混在は構造的に起きない」という主張はライブと backfill の両方で成立していなければ意味がない。
- **予測実行が発走 50 分前より後**(体重公表後): 全馬計量済みなら full-info 条件になる。この条件で現行より悪化していないことが非劣化ガードの役割である。

## Requirements *(mandatory)*

### Functional Requirements

#### 特徴の定義(US1)

- **FR-001**: システムは各出走行に対し、その馬が対象レースより**厳密に前**に出走し、かつ体重が記録されている直近の走の体重を「前走体重」として供給しなければならない。同日の走は供給元にしてはならない。
- **FR-002**: 前走体重の供給元は「出走(started)かつ体重が記録済み」の走に限らなければならない。取消・除外の走で計量されていた体重は供給元にしない。
- **FR-003**: システムは前走体重の**鮮度**(その体重が計測された日から対象レース日までの経過日数)をモデル入力として利用可能にしなければならない。**専用の新規列を作ることは要求しない** — 既存の「前走からの経過日数」がこれと一致することが実測で確認されている限り、それで満たされる。一致しなくなった場合は FR-005a により検知される。
- **FR-004**: システムは前走体重が供給できたか否かを区別できる情報をモデル入力として利用可能にしなければならない。**専用の新規列を作ることは要求しない** — 既存の「過去走の有無」がこれと一致することが実測で確認されている限り、それで満たされる。
- **FR-005a**: システムは「過去に出走がある行で前走体重が欠損する割合」を機械的に検証し、**事前登録した境界を超えたら fail-closed** としなければならない。加えて、許容される例外は**すべて「その馬に計量済みの過去出走が一度も無い」で説明できる**ことを検証しなければならない(率の境界だけでは、解決器が拾えるはずの供給元を落としている不具合を検出できない)。これが FR-003 / FR-004 を既存列で満たしてよい根拠であり、境界超過は専用列の追加を再検討する合図になる。実測では全履歴 862,274 行中 1 行(0.000116%)のみが例外である。
- **FR-005**: 前走体重が存在しない場合、前走体重と鮮度は欠損(Unknown)として渡さなければならない。0・集団平均・その他の代用値で埋めてはならない(憲法 IV)。
- **FR-006**: 既存の当日体重・増減・斤量比率の**値の定義は一切変更してはならない**。当日体重が存在する行では、これらは現行と同一の値でなければならない。これは**特徴量ビルダの出力についての要件**である(FR-034 の可用性正規化は予測経路での入力選択であって、列の定義を変えるものではない)。
- **FR-007**: 前走体重の供給元として、非正値または妥当な体重範囲を外れた記録を採用してはならない。
- **FR-008**: 同一馬・同日に複数の供給元候補が存在する場合、前走体重は欠損としなければならない(暗黙の一方選択を禁止)。
- **FR-009**: 新規に追加する列はすべて浮動小数点型とし、欠損は欠損のまま伝播させなければならない。

#### 学習時の欠損付与(US1)

- **FR-010**: 学習時、体重に関する入力(当日体重・増減・斤量比率)を欠損させる際は、**レース単位で同時に**欠損させなければならない。行単位で独立に欠損させてはならない。
- **FR-011**: 学習時の欠損付与の割合と方式は、評価開始前に固定し、記録しなければならない。割合は**実運用の欠損率を再現する値ではなく、両 regime に学習質量を配分する値**として選ぶ — 予測のほぼすべてが体重なしで行われる(97.4%)という事実は、体重ありの経路を学習させる必要が別にあることと両立しなければならない。選んだ値とその根拠を事前登録する。
- **FR-012**: 欠損付与は決定論的でなければならない(同一設定・同一データで再実行すると同一の欠損パターンになる)。使用した seed を記録する。
- **FR-013**: 欠損を付与した行であっても、**新規列の前走体重と、その鮮度・有無を供給する既存列**は欠損させてはならない(これらは発走前に既知であり、欠損させると feature の目的そのものが失われる)。

#### リーク境界(憲法 II)

- **FR-014**: 前走体重・鮮度・有無は、対象レースの結果・当日オッズ・同日の他レースの情報を一切参照してはならない。対象レースの結果を変更しても、これらの値が変化しないことを機械的に検証しなければならない。
- **FR-015**: 前走体重の解決は、既存の as-of 特徴と同一の時系列規約(厳密前・同日除外)に従わなければならない。
- **FR-016**: 学習時の欠損付与は、そのレースの結果に依存してはならない(結果を見て欠損させる馬を選ばない)。

#### 版管理と serving 互換

- **FR-017**: 特徴量定義版は `features-021` としなければならない(`features-019` は 070 で、`features-020` は 088 で、いずれも bump 後 REJECT により revert された焼却番号であり再利用を禁止する。091 は当初 020 を再利用しており、main 取り込み時に是正した — `feature_hash` は列名から計算されるため再学習は不要で、動いたのはラベルだけである)。
- **FR-018**: 現行 active モデルは、新しい特徴量定義版の下でも従来と**バイト同一**の予測を返さなければならない。互換経路は既存の版固定機構([058](../058-market-history-features/spec.md) の仕組み)を用いる。
- **FR-019**: 新規列は純粋な追加でなければならず、既存列の値を変えてはならない。実データ上で共有列の完全一致を一度実測して確認する。
- **FR-020**: 新規列は既に読み込み済みのソース列のみから導出しなければならない(新しいソース列を読まない)。これによりソース指紋が不変となり、materialize 済み成果物との整合が保たれる。

#### 採用判定(US2)

- **FR-021**: 採否の主判定は **serving regime**(体重 3 列をレース単位でマスクした条件)でのレース単位 winner NLL の paired 差でなければならない。
- **FR-022**: **full-info regime**(体重あり)での非劣化を、独立したガードとして判定しなければならない。主判定とガードの両方が成立した場合にのみ採用とする。
- **FR-023**: 候補と現行の比較は、保存済み指標を読まずに**同一レース集合・同一 fold 境界で同時再評価**しなければならない([068](../068-evaluation-contract-calibration/spec.md) の paired 契約)。
- **FR-024**: 重要 subgroup(直近年・ID 名前空間別など、評価前に固定した少数集合)での非悪化を判定に加えなければならない([069](../069-past-odds-features/spec.md) の subgroup guard)。
- **FR-025**: ゲート設定は本評価の開始前に凍結し、設定の同一性を検証したうえで評価を実行しなければならない。不一致は評価失敗とする。
- **FR-026**: verdict の正本は**単一の事前登録された式**でなければならず、評価レポートはその式を評価した結果を**単一の真偽値フィールドとして出力**しなければならない(読み手が 3 つのパスを自分で AND する余地を残さない)。個別数値を事後に読み替えて採否を主張してはならない。
- **FR-027**: 評価が実行不能な場合の結果は NO_DECISION とし、ボーダーライン上の数値を理由に NO_DECISION としてはならない。
- **FR-028**: 前走体重のカバレッジ監査を、年別・鮮度帯別・出走歴の有無別に出力しなければならない。
- **FR-029**: REJECT の場合、特徴量定義版の引き上げと結線のみを差し戻し、モジュールとその単体テストは負の結果の記録として非結線のまま保全しなければならない(062/070 の前例)。
- **FR-029a**: REJECT の場合、**退避先として「serving 経路での既存 `weight` 列への充当」を検討対象として記録**しなければならない(採用を約束するものではない)。理由: kill-test が測ったのはまさにその構成であり(C−B = −0.012275、CI が 0 を跨がず 6 年全てで有意)、**独立列方式が棄却されても当該証拠は失われない**。ただしその方式は本 spec が却下した既知の欠陥を持つ — 列名が変わらないため `feature_hash` が不変で serving の fail-close が発火せず、古いモデルが黙って新しい意味の値を食う(017 と同型・research D8)。したがって退避先を実際に採る場合は、**入力方針の版を `logic_version` に持たせ、その版を冪等キーにも参加させる**こと(076 の `calib=` と同型)を最低条件とし、別 feature として起こす。
- **FR-030**: ADOPT の場合であっても、昇格は運用者の明示的な承認を経なければならない。

#### 宣言の是正(US3)

- **FR-031**: 斤量を馬体重で割った比率の列の利用可能タイミング宣言を「馬体重後」に是正しなければならない。
- **FR-032**: 宣言の是正によって特徴量の値・列名・列順・特徴量ハッシュが変化してはならない。
- **FR-033**: レジストリ全体を監査し、宣言された利用可能タイミングより遅い入力に依存する列が他に存在しないことを確認しなければならない。存在する場合は同一変更セットで是正するか、是正しない理由を記録する。

#### レース単位の可用性正規化(US1)

- **FR-034**: 予測時、対象レースの出走馬に**一頭でも当日体重が未公表の馬がいる場合、そのレースの全馬**について当日体重に依存する入力を欠損として扱わなければならない。全馬が計測済みの場合にのみ当日体重を使う。これにより、レース内で体重の有無が混在した入力がモデルに渡ることが構造的に起こらなくなる。
- **FR-034a**: FR-034 の正規化は、**予測に使うモデルが前走体重を入力として持つ場合にのみ適用**しなければならない。前走体重を持たないモデル(本 feature 以前に学習された現行モデルを含む)に対しては**何もしてはならない** — 代替値を持たないモデルから当日体重を取り上げるのは、補償のない一方的な劣化であり、SC-004 のバイト不変にも反する。適用可否は「そのモデルの入力列に前走体重が含まれるか」で機械的に決まり、運用フラグや採否の状態に依存しない。
- **FR-034b**: FR-034 の正規化は、予測を行う経路すべて(ライブ・backfill)に**同一の条件で**適用しなければならない。片方だけに適用すると、混在が構造的に起こらないという FR-034 の主張自体が成立しなくなる(確定済レースにも 0.3〜0.4% の体重欠損が残っているため、backfill でも混在は発生しうる)。
- **FR-035**: FR-034 の正規化が発動した回数と、その際の(計測済み頭数 / 出走頭数)の分布を観測できるようにしなければならない。これは正しさの担保ではなく**運用上の可視性**のためである(どれだけ頻繁に full-info を手放しているかを知る)。
- **FR-036**: 前走体重の遡及的な参照が、当時の予測実行時に知り得た値と一致しない場合があること(遅延取込・訂正・個体統合・順延・重複)を前提とし、**タイブレークを決定論的に固定**しなければならない。過去時点のスナップショットを再構成する方法は存在しない(体重の履歴を保存していないため)ので、この限界は明示する。

### Key Entities

- **前走体重 (prev weight)**: その馬が対象レースより厳密に前に出走し、かつ体重が記録されている直近の走における馬体重。当日体重の代理値。
- **体重の鮮度 (weight age)**: 前走体重が計測された日から対象レース日までの経過日数。代理値の劣化度合いを表す。**実測上は既存の「前走からの経過日数」と完全に一致する**ため専用列を作らない。
- **体重の有無 (has prev weight)**: 前走体重を供給できたか否か。デビュー馬と履歴のある馬を区別する。**実測上は既存の「過去走の有無」と完全に一致する**ため専用列を作らない。
- **serving regime**: 体重に関する入力が欠損している条件。実際に予測が行われる条件であり、本 feature の主評価条件。
- **full-info regime**: 体重が公表済みの条件。非劣化ガードの評価条件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 体重が未公表のレースについて、予測の品質(レース単位 winner NLL)が現行より改善し、**その改善量が事前登録した最小効果(0.002)を超え**、かつ開催日クラスタ bootstrap 95% 信頼区間が 0 を跨がない。最小効果を明記するのは、これを欠くと「SC-001 は達成したが verdict は REJECT」という事後の読み替えが可能になるため。
- **SC-002**: 体重が公表済みのレースについて、予測の品質が現行から悪化していない(事前登録した非劣化幅の範囲内)。
- **SC-003**: 事前登録した重要 subgroup のすべてで悪化がない。
- **SC-004**: 現行 active モデルの予測が、変更前後で 1 頭の 1 ビットも変わらない。これは**あらゆる入力条件で**成立する — 現行モデルは前走体重を持たないので FR-034a により可用性正規化の対象外であり、体重が混在するレースでも挙動が変わらない。
- **SC-005**: 出走歴のある馬について、体重未公表時に前走体重が供給される割合が、実 DB の**現在の未確定レース**で 85% を超える(実測 89.8% に対する下限)。確定済レースのカバレッジではなく、**これから予測する行**を母集団として測る。
- **SC-006**: 対象レースの結果・当日オッズ・同日他レースを変更しても、**新規列 `prev_weight`(および鮮度・有無を供給する既存列)**の値が 1 つも変化しない。
- **SC-007**: データベースのスキーマ、外部に公開している契約、および買い目・推奨の生成ロジックが一切変更されていない。
- **SC-008**: 採否の結論が、評価開始前に凍結した単一の基準から一意に導かれており、その基準が評価後に変更されていない。

## Assumptions

- 前走体重は当日体重の実用的な代理になる(競走馬の体重は走間で数 kg 程度しか変動しないため)。kill-test で全馬供給ありの層において実体重との差が winner NLL で +0.001 まで縮むことを確認済み。
- 独立列方式は、kill-test で測定した混入方式(既存 `weight` 列への流し込み)の効果を下回らない。木は体重有無フラグで分岐して混入方式と同じ関数を構成できるため。ただしこれは論理的な期待であり、**実測は本 feature のゲートで行う**。
- 学習時の欠損付与の**割合**は、実運用の欠損率の再現ではなく学習質量の配分として選ぶ(両端は退化する — 0 なら前走体重が当日体重に食われ、1 なら当日体重の経路が未学習になる)。欠損の**発生機序**(体重公表前に予測を実行する)は馬の属性や結果と独立であり、無作為とみなせる。
- 馬体重の公表タイミング(発走約 50 分前)と予測実行の時刻分布(中央値 T−6.7 時間)は、086 で実測した現在の運用が続くものとする。運用が変われば欠損率が変わり、学習時の欠損付与率も見直しが必要になる。
- スキーマ変更・マイグレーション・API 変更・OpenAPI 変更は不要である。新規列はすべて特徴量層で完結し、既存のソース列のみから導出される。
- 採用された場合は新しいモデルの学習が必要になる(新規列は既存の学習済みモデルからは参照できない)。現行 active モデルは互換経路でそのまま動き続ける。
- 067(個体分裂の統合)は未実装であり、`nk:` サロゲートによって履歴が繋がらない馬が存在する。この feature はそれを解決しないが、カバレッジ監査で「真のデビュー」と「履歴断絶」を区別して報告する。

## Out of Scope

- 当日馬体重の早期取得(発走 50 分前より前に体重を得る手段の開拓)。データ供給側の話であり、本 feature はあくまで「得られない前提での最善」を扱う。
- `weight_diff`(当日の増減)の代替。当日体重なしには原理的に再現不能であり、kill-test でその寄与は +0.002470 と測定済み。捏造しない。
