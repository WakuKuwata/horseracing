# Feature Specification: JRDB を主情報源にし、netkeiba を止められる状態にする

**Feature Branch**: `178-jrdb-primary-source`(共有 checkout に未コミット変更が多数あるため、ブランチは切らず main 上に spec だけ置く。実装は別 worktree を推奨=176 と同型)

**Created**: 2026-11-08

**Status**: Draft(2026-11-08 の方針相談を spec に起こし、同日の codex レビュー 6 件を全件採用して改訂=本文末尾「レビュー」。**同日 plan で公開仕様書とサンプルを実測し 3 点を改訂**: 騎手/調教師コードは JRDB 独自、馬別前 3F は 1200m 以外で別定義、利用者方針「JRDB で取れたデータでモデルを作る」を段 3b 再構築として追加=[research.md](research.md) D1/D3/D11)

**Input**: User description: "データソースを JRDB と JRA 公式のみにする。netkeiba を外す。"

## 位置づけ

2025 年半ばに JRA-VAN の年次 CSV が止まり、2026 年のレースは netkeiba のスクレイピングが唯一の情報源になった。2026-11-03 から JRA 公式サイトを第 2 の情報源として並走させている(176)。それでも次の傷が残っている。

| 傷 | 現状 | 原因 |
|---|---|---|
| 馬・騎手・調教師の ID 分裂 | `nk:` サロゲート 5,545 頭 | netkeiba ID は正規 ID に紐付かない |
| 馬ごとのテン3F | 2026 年 0%(1200m の恒等式だけ 99.5%) | netkeiba は馬ごとの上がり3F しか出さない |
| 馬主・生産者 | netkeiba 期 0% | 取っていない |
| race_class の綴り | `1勝` と `１勝` が 51% で分裂 | 供給元の表記差 |
| 取得予算 | 10 秒間隔・ブロック実績・HTTP 400 拒否 | スクレイピング |
| 確定単勝オッズ | netkeiba 結果ページ依存(139) | JRA 公式の結果ページには人気しかない |

**JRDB は「新しい情報源」ではなく、止まった JRA-VAN の後継**として位置づける。JRDB は中央競馬の出馬表(KYI)・成績(SED)・オッズ(OZ 系)・直前情報(TYB)・調教(CYB/CHA)・馬基本(UKC)・騎手/調教師(KZA/CZA)・レース情報(SRB)・払戻(HJC)を Shift_JIS 固定長ファイルで配信し、1999 年〜のアーカイブがある。**馬の血統登録番号は 8 桁→10 桁の決定論で既存 DB の正規 ID と一致する(サンプル 822 行で 100%)が、騎手・調教師コードは JRDB 独自で JRA コードと一致しない**(2026-11-08 実測)。

役割分担:

- **JRDB** = 構造化の一括フィード。出走行とマスタ行を作る責任者。**学習データの正本**(利用者方針 2026-11-08: JRA-VAN の過去データでなく JRDB で取れたデータでモデルを作る。JRDB が JRA-VAN より必ず多く、足りない列が無いことを段 1 で確認する=[contracts/files-and-ids.md §4](contracts/files-and-ids.md) で 48 列すべてに対応あり)。
- **JRA 公式**(176) = 確定値(結果・払戻)と発走直前オッズの権威。
- **netkeiba** = policy で停止できる予備。コードは残す。

**この feature が約束しないこと**: 予測精度・回収率の改善。情報源を替えても 173〜175 で確定した「判断時から締切までに売れて支払価格が下がる」壁は動かない。価値は、正規 ID・同一定義で揃った歴史・取得の安定・2025〜2026 に死んだ列の復旧、の 4 点にある。

## 何を変えるか(段階と順序)

順序は事前登録し、後段の結果を見て前段をやり直さない。

| 段 | 内容 | ゲート |

## 憲法との関係

- **I(ID)**: JRDB の血統登録番号(8 桁)と騎手/調教師コードを正規 ID に写像する規則は決定論で、名前での推測結合はしない。写像できない行は書かずに報告する。
- **II(リーク境界)**: 事後ファイル(SED・SRB・HJC)は対象レース自身の特徴に使わず、将来レースの過去走としてだけ as-of で使う。JRDB の指数類(IDM 等)はオッズを材料にしうるので、勝率モデルの特徴には入れない(市場連動モデル側で扱うなら別 spec)。市場オッズは勝率モデルの特徴にしない。
- **III(評価)**: この feature は採用判定を伴わない。修復が予測に与える波及は 139 と同じ方法で測って記録する(FEATURE_VERSION は原則据え置き)。
- **V(監査・オッズ履歴)**: オッズの履歴は保存しない(単一最新値+判断記録のみ)。JRDB の 10 時オッズ・確定オッズも「単一最新値」の規則に従い、別表を作らない。取込は冪等で、来歴表に供給元を残す。
- **VI(契約)**: API・OpenAPI・front は不変。スキーマ変更は JRDB 固有の生データ保管(要否は plan で判断)と来歴 enum の拡張に限る。

## やってはいけない操作

- 定義の一致を確かめる前に、JRDB の値を既存列に混ぜること(017/091: 同じ列に別定義の値を入れるのは欠損より悪い)。**実測で別定義と分かっている列=`first_3f`(1200m 以外)・`corner_orders`・`running_style`・`sire_line/damsire_line` は現行 DB に書かない**(JRDB 正本の DB でだけ JRDB の定義で持つ)。
- 騎手・調教師を JRDB コードの数字で結合すること(JRA コードと別体系)。名前だけの一致を同一性の証明にすること。
- TYB(発走 15 分前頃)の単複オッズや JRDB 基準オッズ(独自の推定値)を、T−3 の判断記録や `race_horses.odds` の現在値に書くこと。
- 配信ファイルや会員 URL・認証情報をリポジトリ・fixture・ログに置くこと(会員規約 第 5 条)。開催日 08:00〜19:00 に昨年以前のファイルを取りに行くこと(JRDB のアクセス制限)。
- 10 時オッズ・確定オッズ・事後ファイルの値で T−3 の判断記録を埋めること。
- 段 0 の現構成での不成立(netkeiba が行を作っている以上、公式だけでは構造的に揃わない)を、移行後の拒否条件に使うこと。合否は段 3.5 で移行後の構成に対して測る。
- 旧版のファイルが後から届いたときに新しい版の値を巻き戻すこと(版は単調)。
- 既存の判断記録(decision_quotes)を、修復後の値で再計算して置き換えること(append-only・反実仮想は別物として開示する=139/175 の規律)。
- 既存の `nk:` 5,545 頭を本 feature で自動統合すること(067 系の修復として別に扱う。新規分裂を止めるのが本 feature の範囲)。
- 共有 checkout の稼働プロセスが読む共通コード(db/enums・models・upsert・pipeline・politeness・ops・policy)に開催中に触ること(176 と同じ規律)。

## User Scenarios & Testing

### User Story 0 - 現構成を診断する: 公式オッズの適時性と netkeiba 依存の棚卸し (Priority: P1)

運用者が 2 開催日以上、netkeiba を止めずに次の 3 つを記録する。(a) JRA 公式経路で T−3 のオッズが鮮度条件(実行前に固定した下限・上限、発走時刻変更時は変更後の発走時刻基準)を満たして取れたレースの割合と、各レースの取得時刻。行がどの経路で作られたかは問わない。(b) 現在の運用が netkeiba に依存している箇所の一覧(出走行の生成・マスタ行の生成・現在値の供給・ID 写像・結果・確定オッズ・払戻・T−3 取得、のどれか)。(c) JRDB の前日版・当日版・直前版の実到着時刻。

**Why this priority**: netkeiba を外すと T−3 の取得先は JRA 公式だけになる。値が正しくても判断時刻に使えなければ移行は失敗で、それを最初に見る数字が要る(codex)。ただし現構成では公式経路が行を作らないので「公式だけで揃うか」は構造的に測れない。段 0 は診断に留め、合否は段 3.5 で移行後の構成に対して測る(codex #1)。

**Independent Test**: 1 開催日の全レースについて (a) の成否と取得時刻が 1 行ずつ残り、(b) の一覧と (c) の時刻表が出る。

**Acceptance Scenarios**:

1. **Given** 鮮度条件(174 の T−3 捕捉窓と同一=各レースの基準時刻 発走 180 秒前・許容 ±60 秒・近接レースの 60 秒ずらしを含む。公式オッズの `official_at` がその窓内なら有効。独自の秒数を別に決めない=窓と取得時刻がずれると割合が意味を失う)・対象レース集合・計測日数が実行前に固定されている, **When** 診断を流す, **Then** レースごとに公式オッズの取得時刻・発走時刻(変更後)・成否・不成立の理由が記録され、割合が 1 つの数字で出る。
2. **Given** 発走時刻が変更されたレース, **When** 成否を判定する, **Then** 変更後の発走時刻を基準にする。
3. **Given** 診断が終わった, **When** (b) の一覧を読む, **Then** 「行の生成」「現在値」「マスタ」「ID 写像」が区別されており、段 2 で移管すべき責任の一覧として使える。
4. **Given** (c) で直前版が T−3 に間に合わない, **When** 段 3.5 を設計する, **Then** T−3 の取得先は JRA 公式に固定し、JRDB の版は判断記録に使わない。

### User Story 1 - JRDB を読み取り専用で取り込み、既存データと突き合わせる (Priority: P1)

運用者が JRDB のアーカイブ(2007〜2024)と日次ファイルをローカルに置き、1 コマンドで読み込んで、既存 DB の同じレース・同じ馬の値と列ごとに突き合わせた報告を得る。製品テーブルには 1 行も書かない。

**Why this priority**: 段 2 以降の全部がこの報告に依存する。特に `first_3f`(馬ごとのテン3F)は JRDB が実測か推定かが未確認で、一致しなければ別列にしなければならない。

**Independent Test**: 2007〜2024 の任意の 1 年分について、レース数・出走行数・列ごとの一致率(数値は許容差つき・文字列は正規化後)・不一致の例が出る。

**Acceptance Scenarios**:

1. **Given** JRDB ファイル(KYI/SED/SRB/UKC/KZA/CZA/HJC)がある, **When** 読み込む, **Then** レースキー→12 桁 race_id・血統登録番号→10 桁 horse_id・騎手/調教師コード→既存 ID の写像が決定論で行われ、写像できない行は件数と例が報告される。
2. **Given** 重複期間のレース, **When** 突き合わせる, **Then** 着順・タイム・上がり3F・テン3F・確定単勝オッズ・人気・馬体重・斤量・コーナー通過順・脚質・クラス・賞金・馬主・生産者・父/母/母父・ハロンタイム・払戻の各列について一致率と定義差(丸め・欠損の扱い・時期による仕様変更)が出る。
3. **Given** `first_3f` について、仕様書での意味の確認(実測か推定か・丸め・欠損の規則)と、区分別(距離帯×年)の数値一致(既定: 両側非欠損の結合済み完走行で差 ≤ 0.1 秒が各区分 99% 以上)の両方が事前に定めた基準に満たない, **When** 報告を読む, **Then** 段 3 で `first_3f` には書かず、本 feature の書込対象から外す(新しい特徴列は FEATURE_VERSION の bump を伴うので別 spec)。
4. **Given** 片側だけ欠損している行・結合できない行, **When** 一致率を出す, **Then** 分母から除いて別集計(件数)として報告する。
5. **Given** JRDB が同じレースの修正版ファイルを後日配信した, **When** 再読込する, **Then** 内容ハッシュが違うので新しい版として扱われ、変わった列と行数(入力差分)が報告され、配信時刻と取込時刻が残る。

### User Story 2 - JRDB を第 3 の writer にし、出走行とマスタ行の生成責任を移す (Priority: P2)

運用者が開催日の前日と当日に JRDB ファイルを取り込むと、出走行(race_horses)と馬・騎手・調教師のマスタ行が JRDB から正規 ID で作られ、JRA 公式経路(176)はその行に書き込む。netkeiba 経路は同じ行に書くだけで新しい行を作らない。

**Why this priority**: 176 の FR-011a は「公式経路は行もマスタも作らず netkeiba の行に書く」前提で、netkeiba を止めると書き込み先が無くなる。生成責任の移管がないと段 4 に進めない。

**Independent Test**: 本番 DB の複製に 1 開催日を再生し、JRDB→公式→netkeiba の順でも、公式(書込先なしで記録)→JRDB→公式の再取込の順でも、項目別優先規則が決定論で選ぶ項目の最終状態が同じ。「結果は先着保持」のように規則が順序に依存する項目は規則どおりであることを確認し、順序不変は要求しない。保護対象の既存値(JRA-VAN 期の静的項目・確定済みの結果と払戻)は不変。同一入力の 2 回目は変更 0。

**Acceptance Scenarios**:

1. **Given** 前日の KYI がある, **When** 取り込む, **Then** 全レースの出走行が正規 ID で作られ、`nk:` 行は 1 つも増えない。新馬は血統登録番号でマスタ行が作られる。
2. **Given** JRDB の出走行があり公式の出馬表・オッズ・結果が後から来る, **When** 公式を取り込む, **Then** 176 の項目別優先規則どおりに同じ行へ書かれ、来歴表に供給元が残る。
3. **Given** JRDB の取込が遅れたか失敗した, **When** 公式の結果が先に来る, **Then** 書き込み先が無い旨が記録され、後から JRDB を取り込んで公式を再取込すると結果も載る(復旧経路)。
4. **Given** JRDB の当日ファイルが開催日の判断締切までに届かない, **When** 運用者が緊急モードを policy で有効にする, **Then** 公式の出馬表から出走行とマスタ行を正規 ID で作れる(176 FR-011a の暫定規則を緊急時の恒久オプションにする。netkeiba の再開では行不足は直らない=codex #2)。
5. **Given** 既存の `nk:X` 出走行と、JRDB が作ろうとする正規 ID `X` の行が同じ出走を指す, **When** 取り込む, **Then** 176 FR-011a と同じ別名規則で既存行に書き、2 行にしない。
6. **Given** 同じ内容(ハッシュ同一)のファイルを 2 回取り込む, **When** 2 回目, **Then** 製品値の変更 0(来歴の取込記録は増えてよい)。修正版(ハッシュが違う・版が新しい)は変更できる列の規則に従って更新し、旧版が後から届いても巻き戻さない。

### User Story 3 - 2025〜2026 の穴を同じ定義の値で埋める (Priority: P2)

運用者が段 1 で定義一致が確認できた列について、JRDB のアーカイブで 2025〜2026 の欠損を埋める。特徴の版は変えず、埋めた後の充足率と予測への波及を記録する。

**Why this priority**: netkeiba 期(2025-10〜)の現行 DB には、馬主・生産者が 0%(研究 D1)、クラス表記のゆれ(`１勝` 等・098)、発走前オッズが確定値として残った行(139 の修復はアーカイブのある期間だけ)、2026 年以前 NULL の発走時刻がある。これらは段 1 で定義一致を確認できる列で、JRDB のアーカイブから埋められる。**テン3F 系 3 列は対象外**: 公開サンプルの実測で 1200m 以外は別定義と確定しており(FR-005・研究 D10)、現行 DB にはどの経路でも書かない。その復旧は段 3b の JRDB 正本 DB(別定義列として別 DB に入る)と学習窓の変更(別 spec)で扱う。

**Independent Test**: 修復前後で馬主・生産者・クラス・確定単勝オッズ・発走時刻の年別充足率が出て、修復対象外の行がバイト不変。

**Acceptance Scenarios**:

1. **Given** BAC の発走時刻, **When** 2007〜2026 の NULL を埋める, **Then** 既存の非 NULL 値(176 で公式が書いた 2026 年分)は変わらず、年別の充足率が報告される。
2. **Given** 馬主・生産者・クラスコード, **When** 埋める, **Then** netkeiba 期の表記ゆれ(`１勝` 等)が JRDB の値で揃い、既存の JRA-VAN 期の値は変わらない。
3. **Given** 確定単勝オッズ(SED), **When** 139 の経路と同じ規則で書く, **Then** 値が変わる行だけ更新され、公式払戻(official_win_payouts)と整合する。
4. **Given** 修復が終わった, **When** 139 と同じ方法で予測への波及を測る, **Then** 期待回収率の中央値・p90 と注目条件の該当集合の差が記録される。既存の判断記録(decision_quotes・attention_picks)は再計算で置き換えない。
5. **Given** 修復した値に配信時刻(利用可能になった時刻)が付いている, **When** 後から「その判断時点で使えたか」を問う, **Then** 配信時刻から答えられる(現行の特徴経路は race_date 基準の as-of で、利用可能時刻基準への変更は別 spec。この feature では時刻を保存して測れるようにするまで)。

### User Story 3.5 - 移行後の構成で運用成立試験をする (Priority: P2)

運用者が、出走行・マスタ・入力値を netkeiba から一切供給しない隔離環境(本番 DB 複製+JRDB ファイル+公式経路)で、2 開催日以上、JRDB と公式を実到着時刻どおりに並走させる。行生成→T−3 判断記録→結果→確定単勝オッズ→払戻まで全対象レースで揃うこと、JRDB 遅延・未着時に緊急モードで復旧できることを確認する。

**Why this priority**: 段 0 は現構成の診断、段 2 は複製での再生で、どちらも「移行後の構成で判断締切までに揃うか」を検証していない(codex)。段 4 の前に移行後の構成そのものを試す段が要る。

**Independent Test**: 試験した開催日の全レースについて、各入力の供給元・到着時刻・判断締切との差が 1 行ずつ残り、不成立 0 件。

**Acceptance Scenarios**:

1. **Given** 隔離環境と、実到着時刻どおりに再生される JRDB ファイル・公式取得, **When** 2 開催日を流す, **Then** 全対象レースで T−3 判断記録が鮮度条件を満たし、結果・確定単勝オッズ・払戻が揃う。
2. **Given** 1 開催日の JRDB 当日ファイルを意図的に遅らせる, **When** 緊急モードを使う, **Then** 判断締切までに出走行が作られ T−3 記録が残る。
3. **Given** 不成立が 1 件でもある, **When** 段 4 に進むか判断する, **Then** 進まず、原因を記録して段 2〜3.5 をやり直す。

### User Story 4 - netkeiba を止めて、止めても運用が回ることを確認する (Priority: P3)

運用者が policy で netkeiba の取得を止め、1 開催日を JRDB+JRA 公式だけで回す。T−3 の判断記録・当日の結果取込・確定単勝オッズ・払戻が揃うことを確認する。

**Independent Test**: netkeiba を止めた開催日の運用記録に欠測がなく、復旧が必要になった場合の手順が runbook にある。

**Acceptance Scenarios**:

1. **Given** 段 3.5 の運用成立試験が全対象レースで成立(SC-001a・FR-015)し、段 2 のゲート(SC-003/SC-004)が成立している(段 0 の割合は FR-002 のとおり合否に使わない), **When** policy で停止, **Then** netkeiba への要求が 0 件で、出走行・T−3 記録・結果・確定オッズ・払戻が揃う。
2. **Given** JRDB の当日ファイルが来ない, **When** 開催日, **Then** 運用者が判断できる状態表示(どの段が止まっているか)が出て、緊急モード(公式出馬表からの行生成)か netkeiba の再開を policy で選べる。

### Edge Cases

- JRDB のレースキーは年が 2 桁で、12 桁 race_id への変換は年の補完が要る。
- 血統登録番号が 8 桁(年 2 桁)の場合の 10 桁化。1999 年以前生まれ(19xx)と 2000 年以降(20xx)の判定。
- 騎手・調教師コードが JRA コードと同じ体系か(要確認)。違う場合は id_mappings を経由する。
- JRDB の馬別 前3F が推定値だった場合: `first_3f` には書かず別列。推定の算出法・改訂履歴を記録。
- 修正版ファイルの再配信: 既存値が変わる行の件数を報告し、来歴に取込時刻を残す。
- 取消馬・出走除外・競走中止・失格・同着・降着。
- 障害レース・地方交流(JRDB は中央のみ)。
- LZH 展開失敗・Shift_JIS の機種依存文字・固定長の桁ずれ(JRDB の仕様改訂)。
- 10 時オッズ・確定オッズはオッズ履歴ではなく「判断記録」でも「現在値」でもない。保存するなら V の単一最新値の規則に従う(確定オッズは `race_horses.odds` の確定値として 139 の規則)。
- JRDB の契約期間外・解約後にアーカイブを保持してよいか(要確認)。

## Requirements

### Functional Requirements

- **FR-001**: 段 0 の診断は、対象レース集合・鮮度条件(有効なオッズ取得時刻の下限と上限・発走時刻変更時は変更後基準)・計測日数(2 開催日以上)を実行前に固定し、レースごとに公式オッズの取得時刻・成否・理由を記録しなければならない。行の生成元は問わない。
- **FR-002**: 段 0 は診断であり、現構成での不成立を段 4 の拒否条件にしてはならない。段 0 は netkeiba 依存の棚卸し(行の生成・マスタの生成・現在値・ID 写像・結果・確定オッズ・払戻・T−3 取得を区別)と、JRDB 各版の実到着時刻を併せて記録しなければならない。
- **FR-003**: JRDB ファイルの読み込みは、レースキー→12 桁 race_id・血統登録番号 8 桁→10 桁 horse_id を決定論で写像する。**騎手・調教師の JRDB コードは JRA コードと別体系なので、KZA/CZA の名前・生年月日・所属・初免許年を材料に `id_mappings`(source=jrdb)で対応づけ、名前だけの一致は conflict として手動に送る**。未解決の人は出走行を書かないのではなく `jockey_id`/`trainer_id` を NULL にして来歴に残す。写像できないレース(JRA 10 場以外)は書かずに件数と例を報告する。
- **FR-004**: 段 1 の突き合わせは、重複期間 2007〜2024 の全レースを対象に、列ごとに「意味の一致」(仕様書での実測/推定・丸め・欠損規則の確認)と「数値の一致」(事前に定めた区分=距離帯×年ごとの一致率・許容差)を別々に報告し、片側欠損・結合不能行は分母から除いて件数で別掲し、製品テーブルには書き込んではならない。
- **FR-005**: 修復対象の各列は、段 1 で意味と数値の両方の基準を満たした場合に限り書き込める。基準は列ごとに事前に固定する(既定: `first_3f` は差 ≤ 0.1 秒が各区分 99% 以上、カテゴリ列は正規化後 99.5% 一致、確定単勝オッズは完全一致 99.9%)。満たさない列は現行 DB には書かず、JRDB 正本の DB(段 3b)でだけ JRDB の定義で持つ。サンプル実測で既に基準に達しないと分かっている列: `first_3f`(1200m 以外)・`corner_orders`・`running_style`・`sire_line/damsire_line`。
- **FR-006**: 段 2 の JRDB 経路は、出走行と馬・騎手・調教師のマスタ行を正規 ID で作る責任を持ち、`nk:` サロゲートを新たに作ってはならない。
- **FR-007**: 段 2 の JRDB 経路は、176 の項目別優先規則と来歴表を共用し、項目ごとに JRDB の優先順位と更新可能条件を規則表に追加する。順序不変を要求するのは規則が決定論で選ぶ項目(払戻は公式優先・オッズは official_at の新しい方・静的項目は既存値保持)に限り、「結果は先着保持」のように順序に依存する項目は規則どおりであることを確認する。保護対象の既存値(JRA-VAN 期の静的項目・確定済みの結果と払戻)は変えてはならない。
- **FR-007a**: 既存の `nk:X` 出走行と正規 ID `X` の行が同じ出走を指す場合は、176 FR-011a と同じ別名規則で既存行に書き、2 行にしない。
- **FR-008**: 段 2 で JRDB の取込が遅れた場合、公式・netkeiba の取込は書き込み先が無い旨を記録し、JRDB 取込後に公式を再取込して復旧できなければならない。判断締切までに JRDB が届かない場合に備え、公式の出馬表から出走行とマスタ行を正規 ID で作る緊急モードを policy で有効化できなければならない(netkeiba の再開は行不足の復旧にならない)。
- **FR-009**: 冪等性の単位はファイルの内容ハッシュとレースとする。同一ハッシュの 2 回目は製品値の変更 0(来歴の取込記録は増えてよい)。異内容のファイルの新旧を自動で決めてよいのは「速報版→正式版」「日次→バックナンバー」だけで、それ以外は自動適用せず差分を報告して運用者の承認を待つ(HTTP の時刻で新旧を決めない)。部分成功はレース単位で記録し、全レース成功までファイルを適用済みにせず、同じファイルの再投入は未適用のレースだけ処理する。
- **FR-010**: 事後ファイル(SED・SRB・HJC)の値は、対象レース自身の特徴に使ってはならず、将来レースの過去走としてだけ as-of で使う。JRDB の指数類(IDM・各指数)は勝率モデルの特徴に入れてはならない。修復・修正版の値には配信時刻(利用可能になった時刻)を保存する。現行の特徴経路は race_date 基準の as-of であり、利用可能時刻基準への変更は本 feature の範囲外として限界に記録する。
- **FR-011**: 10 時オッズ・確定オッズ・事後ファイルの値で T−3 の判断記録(decision_quotes)を埋めてはならない。
- **FR-012**: オッズの履歴は保存しない。JRDB の各時点オッズは単一最新値の規則に従い、別表を作らない。確定単勝オッズは 139 の規則(値が変わる行のみ・公式払戻と整合)で書く。
- **FR-013**: 段 3 の修復は特徴の版を変えず、修復前後の年別充足率と、139 と同じ方法で測った予測への波及(期待回収率の中央値・p90・注目条件の該当集合の差)を記録しなければならない。既存の判断記録(decision_quotes・attention_picks)は再計算で置き換えず、修復後の値での再構成は反実仮想として別に開示する。
- **FR-014**: netkeiba の取得は policy で停止・再開でき、停止中は netkeiba への要求が 0 件でなければならない。コードは削除しない。
- **FR-015**: 段 4 は、段 3.5 の運用成立試験(netkeiba から一切供給しない隔離環境・2 開催日以上・実到着時刻どおり・JRDB 遅延時の復旧を含む)が対象レース全件で成立したときだけ進める。
- **FR-015a**: 段 3.5 では、各入力(出走行・マスタ・T−3 オッズ・結果・確定単勝オッズ・払戻)の供給元と到着時刻と判断締切との差をレースごとに記録しなければならない。
- **FR-016**: 開催中は稼働プロセスが読む共通コードに触らず、新規ファイルだけで実装を進め、反映は開催終了後に 1 回とする(176 と同じ)。
- **FR-017**: API・OpenAPI・front・admin は不変。スキーマ変更は JRDB 生データの保管(要否は plan で判断)と来歴 enum の拡張に限る。
- **FR-018**: JRDB の利用規約で自動取得・継続取得・DB 保存・解約後の保持が許されているかを契約前に確認し、記録する。[NEEDS CLARIFICATION: 規約の確認結果]

- **FR-021a**: 現行 DB への書込み(通常取込・修正版・修復)は、別定義の 4 列(`first_3f`・`corner_orders`・`running_style`・`sire_line/damsire_line`)を**どの経路でも**書かない。書込み先(現行 / JRDB 正本)は取込の必須引数で、decode と upsert の両方で拒否する。

- **FR-022**: 会員 URL・認証情報・配信ファイル・配信ファイル由来の値を、リポジトリ・テスト fixture・ログ・公開成果物に置かない。テスト fixture は公開サンプル(`/program/`)と合成行に限る。過去ファイルの取得は開催日 08:00〜19:00 を避ける(policy で拒否)。

- **段 3.5 の試験記録**: 開催日・レース・各入力の供給元・到着時刻・判断締切との差・成否。
- **ファイル版**: 内容ハッシュ・版・配信時刻・取込時刻。版は単調。

## Assumptions

- JRDB は契約と費用を伴う。アーカイブは 1999〜現在を取り込み、学習窓は 2007〜 を既定とする(1999〜2006 の利用は別 spec)。会員ページ(Basic 認証)で確認済み(2026-11-08): SED・KYI・UKC・HJC・BAC・TYB・SKB・KAB は 1999〜2025 の年度パック(zip・最新形式)と 1999-01-05 以降の単体ファイル、CYB は 2000〜。直近 1 週間とバックナンバーは置き場が別([research.md D16](research.md))。
- JRDB の血統登録番号は JRA の体系で、既存 10 桁 ID と決定論で対応する(サンプル 822 行で確認済み)。騎手・調教師は対応表が要る。
- JRDB は中央競馬のみを対象とし、地方は扱わない。
- JRA 公式経路(176)は稼働しており、T−3 のオッズ取得先になりうる。
- 既存の `nk:` 5,545 頭の統合は本 feature の範囲外(067 系)。
- JRDB 固有の新情報(調教・直前情報・指数)の特徴化は別 spec。
