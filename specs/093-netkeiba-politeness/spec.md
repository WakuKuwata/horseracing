# Feature Specification: netkeiba 取得礼儀の単一化(真の 1req/分)

**Feature Branch**: `093-netkeiba-politeness`

**Created**: 2026-08-12

**Status**: **Draft**。着手前に **D-1(capture の扱い)の運用者判断が必要**(§3)。

**Input**: 運用者方針 —「netkeiba はアクセス頻度が高いと止められるため 1req/1分などに抑えたい」

---

## 1. 問題:設定された間隔が、実際には一度も強制されていない

`OPS_FETCH_MIN_INTERVAL` は存在するが、**これを 60 に設定しても netkeiba への
リクエスト間隔は 1 秒のままになる経路が 5 つある**。092 の調査で実コードを確認した。

| # | 迂回経路 | 実装上の根拠 |
|---|---|---|
| 1 | **fetcher インスタンスごとに独立**した状態 | `HttpFetcher._last_fetch: dict[domain, ts]` はインスタンス変数 |
| 2 | **ホストごとに独立**したバケット | キーが `_domain(url)`。`race.netkeiba.com` と `db.netkeiba.com` が別枠 |
| 3 | **IO スレッド 2 本**が各自 fetcher を持つ | `OPS_WORKER_CONCURRENCY` 既定 2 |
| 4 | **robots.txt がプロセス内制限を迂回** | `_robot_allows` は `_rate_limit` を呼ばない |
| 5 | **リトライがプロセス内制限を迂回** | `_rate_limit` はリトライループの外で 1 回だけ |
| 6 | **scrape CLI が門の外** | `list-races`/`complete-profiles`/`capture-fixture` は素の `HttpFetcher` |

092 で `make_fetcher()` が `OPS_FETCH_MIN_INTERVAL` を読むようにはしたが、
**それは #1〜#6 のどれも解決していない**。設定値が効いているように見えて効かない状態は、
効かないと分かっている状態より危険である。

### 既にある土台

086 が **DB 経由のプロセス跨ぎスロットル**を作っている:
`fetch_throttle_state(domain PK, next_allowed_at, blocked_until, block_reason)` と
`RequestPoliteness.reserve()`(INSERT ON CONFLICT + SELECT FOR UPDATE + `clock_timestamp()`)。
`CaptureHttpFetcher` が `pre_request` フックで使っている。

**適用点は特定済み**: `HttpFetcher._before_request`(= `pre_request` seam)は
**robots 取得の直前と、リトライループの内側の両方**で呼ばれる。つまり #4/#5 は
`_rate_limit` を直す話ではなく、`pre_request` に DB スロットルを挿せば自動的に閉じる。

---

## 2. なぜ今やるか

- 運用者は 1req/分を **前提として** 日次運用を組もうとしている。前提が成立していない。
- 092 で本賞金の遡及 backfill(2,946 リクエスト)を予定している。**予算を使う前に
  礼儀を確実にしておかないと、backfill 中にブロックされる**。
- ブロックは HTTP 400 で来る([[scrape-refusal-http-400]])。そして **400 には cooldown が
  付いていない**(§4 の欠陥③)。つまり今ブロックされても、日次ジョブは 1 分ごとに
  叩き続ける。

---

## 3. 着手前に必要な運用者判断

### D-1(BLOCKER): 60 秒間隔と対話 capture の 10 秒締切は両立しない

`CaptureHttpFetcher` は robots と本命の 2 リクエストを投げる。60 秒間隔なら本命は
最短でも T+60 にしか送れないが、対話 capture(`predict_manual`)の締切は 10 秒
(`deadline_for`)。**構造的に必ず期限切れになる。**

これは実装の穴ではなく、1req/分 と 086 の設計の非互換である。以下から選ぶ:

| 案 | 内容 | 代償 |
|---|---|---|
| **(a)** | robots.txt を**永続キャッシュ**(TTL 付き)し、capture の実リクエストを 1 本に減らす | robots の鮮度が TTL 分古くなる |
| **(b)** | capture の締切を 60 秒超に延ばす | 予測クリック時の体感が最大 1 分悪化 |
| **(c)** | 1req/分 の間は capture を止める | 荒れ度の前向き検証([[chaos-084-capture-operations]])が進まない |

(a) が最も損失が小さいと考えるが、**運用者の決定事項**。robots は本来ホストごとに
1 回で済むはずのものが、capture が毎回新しい fetcher を作るため毎回取得されている。

### D-2: IO 並列度を 1 にするか

1req/分では **並列度を上げても源のスループットは増えない**(直列化されるため)。
2 本のままだとトランザクションのスケジューリングが複雑になるだけ。
1 本に落とすのが妥当と考えるが確認したい。

## 4. 修正すべき欠陥(092 の調査で確定)

### ① 間隔が「情報源ごとの契約」になっていない [BLOCKER]

capture 側は `min_interval_s=1.0` 既定。**同じスロットル行を共有するので、capture が
予約すると `next_allowed_at` を 1 秒しか進めない**。ops を 60 秒にしても capture が
隣で 1 秒間隔に戻す。参加者ごとに間隔を選ばせている限り、最も弱い設定が勝つ。

→ 間隔は **情報源に属する単一の契約**であるべきで、呼び出し側の引数であってはならない。

### ② 先取り予約はスリープ復帰でバーストする [BLOCKER]

`reserve()` は `next_allowed_at` を**先に進めてからローカルで sleep** する。
2 つの待機者が T+60 と T+120 を予約 → 1 つ目がラップトップスリープで T+110 に起床して
送信 → 2 つ目が T+120 に送信 = **10 秒間隔**。このリポジトリはノート PC で動いており
(worker のエラーバックオフのコメントが "laptop sleep" に言及している)、机上の話ではない。

→ 予約時刻を過ぎていたら**送信直前に取り直す**。任意の未来スロットを先に押さえない。

### ③ HTTP 400 に cooldown が付かない [HIGH]

`_COOLDOWN_S = {429: 30分, 403: 60分}`。**400 が無い。**
一方 `REFUSAL_STATUSES = {400, 403, 429}` で、そこのコメント自身が
「netkeiba は持続的な負荷に空ボディの素の 400 で応じる」と書いている。

**ブロックされたら止まるための仕組みが、実際のブロックのステータスで発火しない。**
外部シグナルの誤分類はこのプロジェクトで 3 回目([[scrape-refusal-http-400]])。

→ ただし 400 は本物のクライアントエラーでもありうる。**空ボディを識別子にする**
(上記コメントの観察)か、400 専用の短めの cooldown にするか、設計時に決める。

### ④ ops に `record_refusal` が無い [HIGH]

`pre_request` だけ配線しても、**429/403 を受けたときに共有 cooldown が入らない**。
別プロセスが次の通常スロットで叩く。`HttpFetcher` に `on_refusal` seam が要る。

### ⑤ `max_wait_s=3.0` は背景ジョブの方針として誤り [HIGH]

待ちが `max_wait_s` を超えると**拒否**する。1req/分なら 2 番目のリクエストの待ちは
約 60 秒なので、3 秒上限では即 `throttle_backlog`。**日次の取込が静かに落ち始める。**

capture(締切あり=待つより諦めるのが正しい)と ops(締切なし=順番を待つのが正しい)で
**モードを分ける**。なお `math.inf` にしても cooldown 中の即時拒否は残るので、
ops は `blocked_until` も待ち抜く必要がある。

### ⑥ ホスト別キーを畳む際、生きている cooldown を取りこぼす [HIGH]

`*.netkeiba.com` を 1 バケットに畳むと、**既存のホスト別行に入っている
`blocked_until` が参照されなくなる**。新しいキーは「即座に送信可能」として初期化される。
**ブロック中に叩き直す**という最悪の挙動。

→ 移行が要る。全 netkeiba 行の `blocked_until` の最大値と `next_allowed_at` の
保守的な最大値を canonical キーに畳んでから切り替える。

### ⑦ 長ジョブの復旧に heartbeat が要る [HIGH]

`recover_stale` は起動時 1 回しか走らない。1req/分では refresh_race が数十分かかる。
092 で stale 窓を広げようとしたが、**広げると孤児が永久に RUNNING で固着する**ことが
分かって revert した(理由はコードのコメントに残してある)。

→ 本来の解は `started_at` ではなく**最終進捗**で判定する heartbeat/lease。
schema 列 1 本と定期的な recovery が要る。

## 5. 要求(FR)

- **FR-001**: netkeiba への**すべての物理 HTTP リクエスト**(robots・全リトライ・全ホスト・
  ops/capture/CLI の全経路)が、単一の共有スロットルを通ること。
- **FR-002**: 間隔は情報源に属する単一の契約であり、呼び出し側が弱い値を選べないこと。
- **FR-003**: `*.netkeiba.com` と apex が 1 バケットを共有すること。無関係なホスト
  (例 `evilnetkeiba.com`)は共有しないこと。
- **FR-004**: `_domain` は変更しないこと(robots URL の組み立てに使われており、
  正規化すると別ホストから robots を取得する)。スロットル専用のキー関数を別に持つ。
- **FR-005**: 予約は**送信直前に有効性を再確認**すること。過ぎたスロットは破棄して
  並び直す。
- **FR-006**: モードを分けること — capture は締切付きで拒否、ops/CLI は無期限待機
  (backlog も cooldown も待ち抜く)。
- **FR-007**: 実 HTTP 拒否(400/403/429)が共有 cooldown を永続化すること。
  400 の扱いは設計時に確定する(§4③)。
- **FR-008**: 移行は**全プロセス停止状態**で行い、既存のホスト別 cooldown を
  canonical キーへ保守的に畳むこと。冪等であること。
- **FR-009**: `RequestPoliteness` の中核を `scrape` へ移設すること。
  **ops は `horseracing_live` を import できない**([test_boundary.py:20](../../ops/tests/integration/test_boundary.py) で機械固定)。
  `live` からは**同一のクラスオブジェクト**を再エクスポートし、`PolitenessRefused` の
  同一性を保つ(ラッパーのサブクラスを作らない)。
- **FR-010**: 長ジョブの復旧を heartbeat/lease 方式にすること(§4⑦)。

## 6. 成功基準(SC)

- **SC-001**: 2 つの fetcher・2 ホスト・robots・リトライを含めて、**すべての物理
  リクエストが 60 秒以上離れる**ことをテストで示す。
- **SC-002**: 弱い間隔を指定した呼び出し側が、60 秒契約を短縮**できない**。
- **SC-003**: 意図的に遅れて起床した待機者(スリープ復帰の模擬)がバーストを起こさない。
- **SC-004**: 背景ジョブは backlog と cooldown を待ち抜き、**失敗/部分成功を生まずに**
  最終的に送信される。
- **SC-005**: 締切付き capture は、未来スロットを消費せずに拒否する。
- **SC-006**: 移行が既存 cooldown の最長値を引き継ぐ。冪等。
- **SC-007**: `live` が公開するクラスと `scrape` が公開するクラスが**同一オブジェクト**。
- **SC-008**: ops の import 境界テストが緑のまま。
- **SC-009**: 素の `HttpFetcher` の既存 rate-limit テストと非 netkeiba 挙動が不変。
- **SC-010**: ワーカーが長ジョブの途中でクラッシュしても、**次の起動を待たずに**復旧する。

## 7. スコープ外

- 遡及 backfill そのもの(092 の続き。本 feature はその前提を整えるだけ)
- 本賞金以外の列の取込(092)
- exotic 価格グリッドの券種構成の見直し
- netkeiba 以外のホストの礼儀方針の変更
- リクエスト予算の削減策(未発走レースへの results 要求のスキップ等。086 の
  「壁時計でなく結果の有無で判定する」という決定に触れるため、別途相談)

## 8. 正直な限界

1req/分では、24 レース × 3 ページ + 券種グリッド + 補完 ≈ **170〜250 リクエスト =
1 日あたり 3〜4 時間**が下限になる。**本 feature はこれを速くしない。**
できるのは「その時間を確実に守る」ことだけである。
容量が足りなければ、券種を減らすか開始を早めるかであって、礼儀を緩めることではない。
